> **Day 4에서는 번역 파이프라인을 실제 메시징 구조로 확장하기 시작했다. 먼저 MessageTransport와 LocalLoopbackTransport로 송수신 경계를 만들고, 이후 원격 스마트폰 통신은 인터넷/Firebase, 개인 주변기기는 BLE라는 물리적 경계를 분명히 했다.**

## 목표: “번역되는 앱”에서 “메시지를 주고받는 시스템”으로

Day 3까지는 원문과 번역의 책임을 분리했다.

송신자는 원문을 만들고, 수신자는 자신의 preferredLanguage를 기준으로 번역한다.

이제 남은 문제는 실제로 그 원문을 **어떻게 전달할 것인가**였다.

UI 안에서 직접 함수를 호출해 상대 메시지처럼 보여주는 방식으로는 실제 네트워크 제품으로 확장하기 어렵다.

그래서 메시지 전달 자체를 하나의 경계로 분리했다.

## MessageTransport

송수신 코드를 특정 네트워크 기술에 바로 묶지 않기 위해 **MessageTransport**라는 계약을 만들었다.

개념적으로 UI와 번역 파이프라인은 transport의 구체적인 구현을 몰라도 된다.

**OutgoingMessage → MessageTransport → IncomingMessage → IncomingMessageProcessor**

이렇게 연결하면 transport는 나중에 교체할 수 있다.

- 개발 중에는 LocalLoopbackTransport
- 실제 사용자 간 통신은 FirebaseMessageTransport
- 미래에 다른 backend가 필요하면 별도 구현체

이 구조를 만든 이유는 “Firebase 앱”을 만드는 것이 아니라 **communication system**을 만드는 것이기 때문이다.

Firebase는 현재 transport 구현 중 하나일 뿐, UI와 번역의 중심이 되어서는 안 된다.

## LocalLoopbackTransport로 먼저 검증

실제 네트워크를 붙이기 전에 **LocalLoopbackTransport**를 만들었다.

내가 입력한 원문을 transport가 상대가 보낸 메시지처럼 다시 돌려주고, 그 메시지가 IncomingMessageProcessor를 거쳐 자동 감지와 번역까지 수행하는 방식이다.

이 과정에서 메시지 ID가 충돌해 ME 메시지와 REMOTE 메시지를 동일한 메시지로 취급하는 문제가 나타났다.

loopback 메시지에 송신 메시지와 구분되는 안정적인 ID를 주도록 수정한 뒤,

**ME 원문 → transport → REMOTE 수신 → 언어 감지 → 수신자 번역 → UI**

흐름이 정상적으로 동작하는 것을 확인했다.

네트워크 없이도 messaging boundary 전체를 먼저 검증할 수 있다는 것이 loopback의 장점이었다.

## Bluetooth와 Internet의 경계를 분명히 하기

프로젝트에는 Bluetooth와 인터넷이 모두 등장한다.

초기에는 이것들이 한 통신 문제처럼 섞여 보일 수 있었다.

하지만 역할을 분리하면 명확하다.

### BLE / Bluetooth

사용자 한 명의 개인 주변기기:

- 허벅지 키보드 → 스마트폰
- 스마트폰 → 스마트글래스

즉 **personal device network**다.

### Internet

서로 떨어져 있는 사용자 사이:

- Smartphone A ↔ Smartphone B
- 대화 메시지
- 친구 관계
- conversation

즉 **user-to-user communication network**다.

이 경계를 명확하게 하면서 “두 스마트폰도 Bluetooth로 연결해야 하나?” 같은 불필요한 복잡성을 제거했다.

원격 사용자 통신은 인터넷을 사용하고, BLE는 사용자의 주변기기에 집중한다.

## Firebase를 실제 backend 후보로 연결하기 시작

원격 transport로는 **Firebase Authentication + Cloud Firestore**를 선택했다.

초기 설정 단계에서 수행한 작업은 다음과 같다.

- Firebase project 연결
- Android 앱 Firebase 설정
- Anonymous Authentication 활성화
- 익명 로그인 후 UID 확인
- Cloud Firestore 생성
- Firestore write 테스트
- 보안 규칙과 conversation 구조 검토

Anonymous Auth를 먼저 사용한 이유는 회원가입 UI를 만드는 데 시간을 쓰지 않고도, 각 앱 인스턴스에 안정적인 user identity를 부여해 메시징을 검증할 수 있기 때문이다.

실제 계정 시스템은 이후 확장할 수 있지만, transport 개발에는 우선 UID가 필요했다.

## Firestore에는 무엇을 보낼 것인가

Day 3에서 정한 원칙을 그대로 유지했다.

**네트워크로 보내는 canonical message는 원문이다.**

번역 결과를 서버에 미리 저장해 상대방에게 전달하지 않는다.

이렇게 하면 수신 기기가 자신의 언어 설정과 로컬 번역 엔진을 기준으로 처리할 수 있다.

당시의 목표 message flow는 다음과 같았다.

**Phone A**
원문 작성  
→ Firestore 전송

**Phone B**
원문 수신  
→ LanguageDetector  
→ ML Kit on-device translation  
→ 원문 + 번역문 표시

이 구조는 privacy와 offline fallback 측면에서도 유리하다. 서버가 모든 사용자의 모든 번역 조합을 만들 필요가 없다.

## 이날 어디까지 갔는가

Day 4에서 LocalLoopbackTransport와 수신측 번역 파이프라인은 실제로 검증했다.

Firebase 쪽은 Auth와 Firestore 기본 연결, UID 확인, write 테스트까지 진행했다.

다만 **FirebaseMessageTransport 전체를 완성해 두 기기 간 실시간 messaging을 검증하는 작업은 다음 개발 단계로 남았다.**

이 구분은 중요하다.

Firebase project가 연결됐다고 해서 실제 user-to-user realtime messaging이 완성된 것은 아니다.

## Verification

실제로 확인한 내용:

- MessageTransport abstraction
- LocalLoopbackTransport 구현
- loopback message ID 충돌 발견 및 수정
- ME 원문 → REMOTE 수신 → receiver-side 번역 흐름 확인
- 개인 주변기기 BLE / 원격 사용자 Internet 경계 확정
- Firebase Anonymous Auth 연결
- 익명 사용자 UID 발급 확인
- Cloud Firestore 연결 및 write 테스트
- Firestore에는 원문을 전달한다는 canonical-message 원칙 유지

아직 남은 것:

- FirebaseMessageTransport 완성
- 두 Android 인스턴스 간 bidirectional realtime messaging
- 실제 conversation 단위 메시지 격리
- participant 권한 검증
- listener lifecycle 검증

## What I Learned

기능 하나를 직접 구현하는 것보다, **경계를 어디에 두는지**가 시스템 확장성에 더 큰 영향을 준다.

MessageTransport를 만들자 UI, 번역, 네트워크를 서로 독립적으로 생각할 수 있게 됐다.

또 Bluetooth와 인터넷의 역할을 나누면서 하드웨어와 서버 구조도 훨씬 단순해졌다.

> **키보드와 안경은 사용자의 주변기기다. 상대 사용자는 인터넷 너머의 participant다.**

이 한 문장이 이후 통신 아키텍처의 기준이 되었다.
