> **Day 2에서는 Day 1의 설계 결정을 실제 Android 코드로 옮겼다. 언어 감지부터 ML Kit 번역, 모델 다운로드와 lifecycle, Compose 대화 UI까지 연결했고, 에뮬레이터에서 한·영·일 양방향 번역과 offline 동작을 직접 확인했다.**

## 목표: “가능할 것 같다”를 실제 Android 동작으로 바꾸기

Day 1에서 기존 Python/ONNX 프로토타입을 현재 제품의 기반으로 사용하지 않기로 결정했다.

그 다음 질문은 단순했다.

> **Google ML Kit를 이용해 실제 Android 앱에서 온디바이스 번역을 끝까지 연결할 수 있는가?**

이날은 이 질문에 답하기 위한 Proof of Concept를 만들었다.

프로젝트를 Android/Kotlin 기반으로 시작하고, Jetpack Compose UI 위에 번역 파이프라인을 단계적으로 붙였다.

## 첫 번째 파이프라인

초기 Android PoC의 핵심 구성은 다음과 같았다.

- **LanguageDetector**: 입력 문자열의 언어 자동 감지
- **TranslationEngine**: 번역 엔진 추상화
- **MlKitTranslationEngine**: ML Kit 실제 구현체
- **TranslationPipeline**: 감지 → 번역 흐름을 연결
- **CommunicationMessage**: 대화 메시지 표현
- Compose 기반 대화 화면

이 구조에서 UI가 ML Kit API를 직접 호출하지 않도록 했다.

번역 기술을 나중에 바꾸더라도 UI와 대화 로직 전체를 뜯어고치지 않기 위해, 처음부터 번역을 하나의 engine boundary 뒤에 두는 것이 목표였다.

## 첫 성공: Korean → English

가장 먼저 확인한 것은 한국어 문장을 영어로 변환하는 단순 경로였다.

ML Kit 번역 모델을 내려받은 뒤 에뮬레이터에서 실제 번역 결과가 나오기 시작했다.

중요했던 것은 사전에 정해 둔 단어를 치환하는 것이 아니라, **처음 입력하는 일반 문장이 실제 모델을 통해 번역되었다는 점**이었다.

이 단계에서 초기 Python 프로토타입과 제품 코드의 차이가 명확해졌다.

이제 번역 결과는 작은 vocabulary JSON이 아니라 실제 온디바이스 번역 모델에서 생성됐다.

## 한·영·일 6방향 테스트

한 방향만 되는 것으로는 충분하지 않았다.

초기 핵심 언어였던 한국어, 영어, 일본어를 대상으로 다음 여섯 방향을 테스트했다.

- 한국어 → 영어
- 영어 → 한국어
- 한국어 → 일본어
- 일본어 → 한국어
- 영어 → 일본어
- 일본어 → 영어

에뮬레이터에서 이 여섯 방향의 번역을 확인했다.

그 후 언어 지원을 특정 세 언어에 고정하지 않기 위해 ML Kit가 제공하는 언어 목록을 동적으로 다루는 방향으로 수정했고, 독일어 번역까지 추가로 확인했다.

이 경험은 프로젝트를 “한국어·영어·일본어 번역기”로 고정하지 않는 중요한 계기가 됐다.

## Offline 검증

이 프로젝트에서 on-device라는 말은 단순한 마케팅 문구가 되어서는 안 됐다.

모델이 다운로드된 뒤 네트워크에 의존하지 않고 새로운 문장이 번역되는지 확인했다.

offline 상태에서도 번역이 계속 동작하는 것을 확인하면서, ML Kit를 현재 제품의 기본 로컬 번역 엔진으로 채택할 수 있는 근거가 생겼다.

물론 이것은 “모든 언어 모델이 항상 설치되어 있다”는 뜻은 아니다.

필요한 언어 모델은 먼저 다운로드되어야 하고, 모델이 없는 상황과 다운로드 실패에 대한 UX는 이후 별도로 다뤄야 한다.

## 모델 lifecycle도 직접 확인하기

온디바이스 모델은 다운로드만 되면 끝나는 것이 아니다.

이날은 모델 관리도 테스트했다.

- 필요한 언어 모델 다운로드
- 특정 모델 삭제
- 다시 다운로드
- 번역 재실행

특히 일본어 모델을 삭제한 뒤 재설치하고 다시 번역이 동작하는 흐름을 확인했다.

이를 통해 앱이 단순히 한 번 성공한 상태에 의존하는 것이 아니라, 모델 lifecycle을 실제 제품 기능으로 다뤄야 한다는 것을 확인했다.

## 자동 언어 감지

사용자가 매번 “지금 들어온 문장은 일본어”라고 지정하는 UX는 실제 대화에 맞지 않는다.

그래서 **LanguageDetector**를 파이프라인에 넣어 입력 문장의 언어를 먼저 감지하고, 감지 결과에 따라 적절한 번역 pair를 선택하도록 했다.

이것이 나중에 수신자 중심 번역 구조에서 매우 중요한 역할을 하게 된다.

상대방이 어느 언어를 쓰는지 미리 고정하지 않고도, 받은 원문을 감지한 뒤 사용자의 선호 언어로 바꿀 수 있기 때문이다.

## 대화 UI: ME / REMOTE 말풍선

번역 테스트를 단순한 입력창과 결과 텍스트로 끝내지 않고, 실제 커뮤니케이션 제품의 형태를 조금씩 만들기 시작했다.

대화 내역을 **ME / REMOTE** 말풍선으로 표시하고 메시지가 누적되도록 했다.

이 과정에서 Compose 화면의 부모 **Column**에 적용했던 vertical scroll 때문에 말풍선 표시가 기대대로 나오지 않는 문제가 있었다.

원인을 확인한 뒤 부모의 불필요한 스크롤 구조를 제거하면서 대화 화면이 정상적으로 표시되었다.

작은 UI 문제였지만 중요한 교훈이 있었다.

번역 엔진이 잘 동작해도 사용자가 결과를 안정적으로 볼 수 없다면 제품 파이프라인은 완성된 것이 아니다.

## 제품의 물리적 역할도 정리하다

이날 장치별 역할도 더 구체화했다.

### Smartphone Companion / Core

입력:
- 스마트폰 키보드
- 스마트폰 마이크
- 향후 허벅지 BLE 키보드

출력:
- 스마트폰 대화 UI
- 스마트폰 스피커 TTS
- 향후 스마트글래스

### Smart-glasses app

스마트폰과 별도 애플리케이션으로 두고, 현재 설계에서는 **시각 출력 역할에 집중**시키는 방향을 잡았다.

복잡한 AI 처리나 음성 처리를 안경으로 밀어 넣기보다 스마트폰을 시스템의 brain으로 유지하는 편이 현실적이었다.

## Verification

이날 실제로 확인한 것:

- Android/Kotlin PoC 구동
- ML Kit 번역 모델 다운로드
- Korean → English 실제 번역
- 한국어·영어·일본어 6방향 번역
- 독일어까지 확장 가능성 확인
- 다운로드된 모델을 이용한 offline 번역
- 모델 삭제 → 재다운로드 → 번역 재개
- LanguageDetector 연결
- TranslationEngine / MlKitTranslationEngine 구조
- Compose ME / REMOTE 대화 UI
- 스크롤 구조 문제 수정 후 말풍선 표시 정상화

당시 실기기 Galaxy 검증은 별도의 후속 과제로 남아 있었고, 이 날의 주요 실행 검증은 에뮬레이터 중심이었다.

## What I Learned

Day 1에서 “기술 이름을 믿지 말고 실제 실행 경로를 확인하자”고 정했다면, Day 2에서는 그 기준을 바로 적용했다.

**On-device translation이라고 부르려면 실제로 모델을 다운로드하고, 네트워크 없이 새로운 문장을 번역해 봐야 한다.**

또 하나의 중요한 변화는 언어였다.

처음에는 한국어·영어·일본어가 프로젝트의 언어 범위처럼 보였지만, 실제 구현을 해보니 시스템을 세 언어로 고정할 이유가 없었다.

이 프로젝트는 점점 “3개 국어 번역기”가 아니라 **언어가 확장 가능한 communication system**으로 바뀌기 시작했다.
