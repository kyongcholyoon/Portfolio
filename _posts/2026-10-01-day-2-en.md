> **On Day 2, I turned the architectural decisions from Day 1 into working Android code. I connected language detection, ML Kit translation, model download and lifecycle handling, and a Compose conversation UI, then verified Korean, English, and Japanese translation in both directions and tested offline behavior in the emulator.**

## Goal: turn “this should work” into an actual Android pipeline

On Day 1, I decided not to use the existing Python/ONNX prototype as the foundation of the product.

The next question was simple:

> **Can Google ML Kit power a complete on-device translation flow inside a real Android application?**

Day 2 was about building a proof of concept that could answer that question.

I started from an Android/Kotlin codebase and gradually connected the translation pipeline to a Jetpack Compose UI.

## The first pipeline

The core pieces of the initial Android PoC were:

- **LanguageDetector** — detects the language of an input string
- **TranslationEngine** — abstraction for translation backends
- **MlKitTranslationEngine** — ML Kit implementation
- **TranslationPipeline** — connects detection and translation
- **CommunicationMessage** — message representation
- Compose-based conversation UI

I intentionally avoided calling ML Kit directly from the UI.

The goal was to place translation behind an engine boundary so that replacing the backend later would not require rewriting the conversation layer.

## First success: Korean → English

The first path I verified was a simple Korean-to-English translation.

After downloading the required ML Kit model, the emulator began returning real translation results.

The important difference from the legacy prototype was that the output was no longer based on replacing pre-defined words.

**Previously unseen sentences were being translated by an actual on-device model.**

That made the boundary between the prototype and the product code very clear.

## Testing all six directions across Korean, English, and Japanese

One direction was not enough.

For the three initial languages—Korean, English, and Japanese—I tested all six combinations:

- Korean → English
- English → Korean
- Korean → Japanese
- Japanese → Korean
- English → Japanese
- Japanese → English

All six directions were verified in the emulator.

After that, I moved away from hard-coding the system around only three languages. I began treating the ML Kit-supported language list dynamically and also verified German translation.

That was an important step away from thinking of the product as a “Korean-English-Japanese translator.”

## Offline verification

For this project, “on-device” could not just be a marketing label.

After the required model had been downloaded, I checked whether the system could translate a new sentence without relying on the network.

Translation continued to work offline.

That gave me a concrete reason to use ML Kit as the default local translation engine for the current product.

Of course, offline translation does not mean every language model is always present. A model still needs to be downloaded first, and the UX for missing models or failed downloads remains a separate product concern.

## Testing model lifecycle

An on-device model is not simply downloaded once and forgotten.

I also tested model management:

- download a required language model
- delete a model
- download it again
- resume translation

In particular, I removed the Japanese model, reinstalled it, and confirmed that translation worked again.

This made model lifecycle management a real product requirement rather than an implementation detail.

## Automatic language detection

A real conversation should not require the user to manually declare, “This message is Japanese.”

I therefore placed **LanguageDetector** in front of the translation engine.

The pipeline first detects the source language, then selects the translation pair.

That decision later becomes central to receiver-side translation, because the recipient can translate an incoming original into their own preferred language without pre-configuring the sender's language.

## Conversation UI: ME / REMOTE bubbles

I did not want the translation PoC to end as a single input box with a single result field.

I started shaping it into a communication product by accumulating messages in **ME / REMOTE** conversation bubbles.

During this work, a Compose layout problem appeared: a vertical scroll applied to the parent **Column** interfered with the bubble layout.

Removing the unnecessary parent scrolling structure fixed the display.

It was a small UI issue, but an important reminder:

a translation engine is not a product if the user cannot reliably see and follow the conversation.

## Clarifying the role of each device

The system roles also became more concrete on this day.

### Smartphone Companion / Core

Inputs:
- smartphone keyboard
- smartphone microphone
- future thigh-mounted BLE keyboard

Outputs:
- smartphone conversation UI
- smartphone speaker for TTS
- future smart-glasses output

### Smart-glasses app

The glasses would remain a separate application and, in the current architecture, focus on **visual output**.

Rather than distributing heavy AI and audio responsibilities across peripherals, the smartphone would remain the system brain.

## Verification

What I actually verified on Day 2:

- Android/Kotlin PoC running
- ML Kit model download
- real Korean → English translation
- all six Korean/English/Japanese translation directions
- extension to German
- offline translation using downloaded models
- model deletion → re-download → translation recovery
- LanguageDetector integration
- TranslationEngine / MlKitTranslationEngine separation
- Compose ME / REMOTE conversation UI
- bubble display fixed after correcting the scroll structure

At this point, Galaxy real-device validation was still a follow-up item. The main runtime verification on Day 2 was emulator-based.

## What I Learned

Day 1 established a rule: do not trust technology labels; verify the actual execution path.

Day 2 applied that rule immediately.

**If I call something on-device translation, I should download the model, disconnect the network, and translate a new sentence.**

Another important shift involved language scope.

The project began with Korean, English, and Japanese in mind, but implementation showed that there was no good reason to lock the architecture to those three languages.

The product was beginning to evolve from a “three-language translator” into a **language-extensible communication system**.

## Next

The next architectural question was ownership:

> **Should translation happen on the sender or on the receiver?**

If users should only need to select their own language, and not configure the language of every conversation partner, messaging and translation responsibilities need to be separated more carefully.

The next step is to design a **receiver-side translation architecture**.
