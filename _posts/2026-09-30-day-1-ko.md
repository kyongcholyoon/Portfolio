> **Day 1의 핵심은 코드를 더 붙이는 것이 아니라, 기존 프로토타입이 실제 제품의 기반으로 쓸 수 있는지 냉정하게 검증하는 일이었다. 결론은 ‘아니다’였고, 그 판단 덕분에 Android 중심 구조로 다시 출발할 수 있었다.**

## 문제: 프로토타입은 동작해 보였지만, 정말 번역 시스템이었는가

초기 프로토타입은 Python, ONNX 모델, 단어장 JSON, NPU 관련 모듈, HUD 출력 모듈 등 여러 파일로 구성되어 있었다. 겉으로 보면 이미 온디바이스 번역 시스템의 뼈대가 있는 것처럼 보였다.

하지만 포트폴리오 프로젝트를 실제 제품 수준으로 발전시키려면 먼저 한 가지를 확인해야 했다.

**현재 코드가 실제로 무엇을 하고 있는가?**

파일을 하나씩 분석하면서 데이터가 어떤 경로로 흐르는지 추적했다. 그 결과, 당시 ONNX 파일은 실제 번역 품질을 내는 학습된 번역 모델로 사용되고 있지 않았고, **npu_engine.py** 역시 이름과 달리 NPU 가속이 아니라 CPU 실행 경로를 사용하고 있었다. 최종 텍스트는 모델 출력보다 제한된 단어장 매핑과 치환 로직에 크게 의존했다.

즉 당시 구조는 **제품용 번역 엔진이라기보다 파이프라인 형태를 확인하기 위한 프로토타입**에 가까웠다.

또한 Gemini API 경로도 포함되어 있었는데, 이는 “인터넷이 없어도 동작해야 한다”는 프로젝트의 핵심 목표와 충돌했다.

## 결정: 기존 코드를 억지로 연장하지 않는다

여기서 중요한 결정을 내렸다.

기존 Python/ONNX 코드를 조금씩 수선해 Android 앱으로 끌고 가는 대신, 그것을 **역사적인 프로토타입으로 남기고 제품 코드는 새로 시작**하기로 했다.

이 결정은 기존 작업을 버리는 것이 아니라 역할을 분명히 하는 일이었다.

- Python/ONNX 프로토타입: 아이디어와 데이터 흐름을 실험한 초기 단계
- Android 앱: 실제 사용자를 대상으로 발전시킬 제품 코드
- 향후 NPU 연구: 모델 경량화와 하드웨어 가속을 검증하는 별도 기술 트랙

특히 “NPU를 사용했다”는 표현은 실제 실행 provider와 profiling으로 확인하기 전까지 사용하지 않기로 했다. ONNX 모델을 Android에 넣었다는 사실만으로 NPU 추론이 되는 것은 아니기 때문이다.

## 현재 제품의 중심을 스마트폰으로 재정의

이날 프로젝트의 기본 데이터 흐름도 다시 정리했다.

초기 목표는 다음과 같았다.

**허벅지 키보드 → Bluetooth → 스마트폰 → 오프라인 번역 → 상대방 앱 → 스마트글래스 또는 스피커**

여기서 스마트폰을 단순 중계 장치가 아니라 **Communication Core**로 두기로 했다.

스마트폰이 담당할 영역은 다음과 같다.

- 텍스트 입력 처리
- 음성 입력과 STT
- 번역
- 메시지 송수신
- TTS
- 대화 상태 관리
- 이후의 Edge AI / NPU 처리

반면 허벅지 키보드는 입력 장치, 스마트글래스는 시각 출력 장치로 역할을 단순하게 유지하는 방향을 잡았다.

이 구조는 이후 프로젝트가 커지더라도 중앙 처리 로직을 스마트폰에 집중할 수 있다는 장점이 있다.

## 번역 엔진: 먼저 검증된 기술로 제품을 세운다

새 Android 제품의 첫 번역 엔진으로 **Google ML Kit On-device Translation**을 사용하기로 했다.

이 선택에는 이유가 있었다.

우선 필요한 것은 “내가 번역 모델을 만들었다”는 문장이 아니라,

**실제 Android 기기에서 모델을 내려받고, 인터넷이 없어도 번역하고, UI와 연결되는 제품 파이프라인이 동작하는가**

를 확인하는 것이었다.

그래서 구조를 특정 엔진에 묶지 않기 위해 **TranslationEngine** 추상화를 두고,

- 현재: **MlKitTranslationEngine**
- 미래: 다른 온디바이스 엔진
- 필요 시: Cloud AI 번역

으로 교체 가능한 방향을 잡았다.

당시에는 자체 ONNX/NPU 번역 엔진도 향후 후보로 남겨두었지만, 이것을 현재 제품의 필수 조건으로 두지는 않았다.

## 초기 메시지 흐름에 대한 가정

이 단계에서는 송신 쪽에서 번역한 결과를 상대에게 전달하는 구조도 검토했다.

하지만 사용자 언어가 늘어나고 각 사용자가 자신의 선호 언어를 가지게 되면 송신자가 상대 언어를 알아야 하는 구조는 확장성이 떨어질 수 있다.

이 문제는 아직 이날 완전히 해결하지 않았다. 대신 **메시징과 번역을 분리할 수 있는 구조가 필요하다**는 사실을 확인했다.

이 판단은 며칠 뒤 수신자 중심 번역 구조로 이어진다.

## Verification

Day 1에서 가장 중요한 결과는 기능 데모보다 **기존 코드의 실제 역할을 확인한 것**이었다.

확인한 내용:

- 기존 ONNX/Python 구조는 현재 Android 제품의 기반으로 사용하지 않음
- 기존 모델/단어장 기반 출력은 실제 범용 번역 제품으로 부족함
- CPU 실행 경로를 NPU 가속으로 표현해서는 안 됨
- Gemini 의존 경로는 offline-first 목표와 충돌
- Android/Kotlin 기반으로 제품 코드를 다시 시작
- ML Kit on-device translation을 첫 검증 엔진으로 선택
- 번역 엔진을 추상화해 이후 교체 가능하도록 설계

아직 실제 Android 번역 앱의 성공 여부는 다음 단계에서 검증해야 했다.

## What I Learned

프로토타입이 많은 파일과 복잡한 이름을 가지고 있다고 해서 제품에 가까운 것은 아니다.

오히려 중요한 것은 다음 질문이었다.

> **이 코드가 실제로 보장하는 것은 무엇인가?**

AI 모델, NPU, Edge AI 같은 단어를 포트폴리오에 넣는 것보다, 실행 경로와 한계를 확인하고 잘못된 가정을 제거하는 편이 훨씬 중요했다.

Day 1은 개발량 자체보다 **프로젝트의 기술적 기준선을 다시 세운 날**이었다.
