> **The key task on Day 1 was not adding more code. It was deciding whether the existing prototype could actually serve as the foundation of a product. The answer was no, and that decision made it possible to restart around an Android-first architecture.**

## Problem: the prototype looked like a translation system, but what did it actually do?

The early prototype consisted of Python code, ONNX model files, a vocabulary JSON file, NPU-related modules, and HUD output components. At first glance, it looked as though an on-device translation stack was already taking shape.

Before turning it into a serious portfolio project, however, I needed to answer a more basic question.

**What does the current code really do?**

I traced the data flow file by file. The audit showed that the ONNX files were not functioning as a practical trained translation model, and **npu_engine.py**, despite its name, was using a CPU execution path rather than verified NPU acceleration. The final text output depended heavily on a small vocabulary mapping and substitution logic rather than meaningful model inference.

In other words, the system was closer to a **prototype for exploring the shape of a pipeline** than to a production translation engine.

The prototype also contained a Gemini API path, which conflicted with one of the project's core goals: remaining useful when no network connection is available.

## Decision: do not force the old prototype into the product

I made an important architectural decision.

Instead of gradually patching the Python/ONNX code and dragging it into an Android application, I would keep it as a **historical prototype and restart the product implementation cleanly**.

That did not make the earlier work useless. It clarified its role.

- Python/ONNX prototype: early experimentation with ideas and data flow
- Android app: the actual product codebase
- Future NPU work: a separate technical track for model optimization and hardware acceleration

I also decided not to claim that the system was using an NPU until the actual execution provider and profiling data proved it. Putting an ONNX model into an Android project does not automatically mean inference is running on an NPU.

## Redefining the smartphone as the system core

The basic end-to-end flow was also reorganized.

The early concept looked like this:

**Thigh-mounted keyboard → Bluetooth → smartphone → offline translation → peer app → smart glasses or speaker**

The smartphone would no longer be treated as a passive relay. It would become the **Communication Core**.

Its responsibilities would include:

- text input processing
- voice input and STT
- translation
- message transport
- TTS
- conversation state
- future Edge AI / NPU processing

The thigh-mounted keyboard would remain an input device, while smart glasses would remain a visual output device.

Centralizing intelligence in the smartphone would make the system easier to evolve without pushing unnecessary complexity into every peripheral.

## Translation engine: build the product on proven technology first

For the first Android translation engine, I chose **Google ML Kit On-device Translation**.

The immediate goal was not to say, “I built my own translation model.”

The real question was:

**Can an Android device download a model, translate without the internet, and connect that translation pipeline to a usable UI?**

To avoid tying the product to one provider, I also planned a **TranslationEngine** abstraction:

- current: **MlKitTranslationEngine**
- future: another on-device engine
- optional: Cloud AI translation

A custom ONNX/NPU translation backend remained a possible research path, but it was no longer a requirement for the product itself.

## Early assumption about message flow

At this stage, I also considered translating on the sender side and delivering the translated result to the peer.

That approach looked simple at first, but it created a scalability problem. If every user can choose a preferred language, the sender should not have to know and manage the recipient's language configuration.

I did not fully solve that problem on Day 1, but I identified an important design requirement:

**messaging and translation should be separable concerns.**

That insight would lead to receiver-side translation a few days later.

## Verification

The most important result of Day 1 was not a flashy demo. It was a clearer understanding of what the existing code did and did not guarantee.

Confirmed decisions and findings:

- the legacy Python/ONNX stack would not be the foundation of the Android product
- the existing model/vocabulary path was not sufficient for general-purpose translation
- a CPU execution path must not be described as NPU acceleration
- Gemini dependence conflicted with the offline-first requirement
- product development would restart around Android/Kotlin
- ML Kit on-device translation would be the first real translation backend
- translation would be abstracted so the backend could change later

The actual Android translation pipeline still needed to be built and verified next.

## What I Learned

A prototype does not become more product-ready just because it contains many files or advanced-sounding component names.

The more useful question is:

> **What does this code actually guarantee?**

For a portfolio, verifying execution paths and removing false assumptions is more valuable than collecting terms such as AI, NPU, and Edge AI.

Day 1 was less about the amount of code written and more about **resetting the technical baseline of the project**.

## Next

The next goal was straightforward:

**Build a real on-device translation pipeline on Android.**

That meant connecting language detection, ML Kit model download, translation, model lifecycle management, and a Compose UI—and then verifying that the translation still worked offline.
