## 1. 기능보다 어려운 것은 Lifecycle이었다

실시간 번역 메시징 앱을 만들면서 점점 분명해지는 것이 있다.

번역 자체만 구현하는 것은 프로젝트 전체에서 가장 어려운 문제가 아니다.

더 어려운 것은 다음과 같은 질문이다.

- 사용자가 로그아웃했는데 이전 계정의 Firebase callback이 늦게 도착하면?
- 번역 언어를 A → B → A로 빠르게 바꾸면?
- 오래된 메시지를 불러오는 동안 realtime message가 들어오면?
- Friends나 Profile로 이동했다가 Chat으로 돌아오면?
- ViewModel이 종료된 뒤 ML Kit callback이 도착하면?
- 이전 conversation의 상태가 새로운 conversation에 섞이면?

이런 문제는 각각 작은 버그처럼 보인다.

하지만 실제 제품에서는 race condition 하나가 다른 사용자의 상태 노출, 잘못된 번역 표시, 중복 listener, 사라진 메시지, 잘못된 대화 진입으로 이어질 수 있다.

오늘은 이 경계를 정리하는 날이었다.

## 2. Auth State를 ViewModel Lifecycle 안으로 가져오기

기존 구조에서는 인증 상태 변화와 communication state 사이의 소유권을 더 명확히 할 필요가 있었다.

이번 작업에서는 ConversationViewModel이 Firebase auth-state listener를 직접 소유하도록 정리했다.

계정이 바뀌면 단순히 userId만 교체하는 것이 아니라 다음 작업들이 함께 무효화되어야 한다.

- 기존 transport listener 중단
- conversation operation 무효화
- pending profile callback 무효화
- pagination 작업 무효화
- translation generation 무효화
- 화면에 남아 있던 이전 계정 메시지 제거
- 이전 account-owned state 제거

핵심 원칙은 간단하다.

> **비동기 작업이 시작될 때의 사용자와, 작업이 완료될 때의 사용자가 같다는 보장은 없다.**

그래서 callback이 돌아올 때마다 현재 auth generation과 UID를 다시 확인하도록 했다.

비동기 앱에서는 callback을 받았다는 사실보다 **그 callback이 아직 유효한가**가 더 중요하다.

## 3. Receiver Language 변경은 단순한 설정 변경이 아니었다

사용자의 preferredLanguage가 바뀌었을 때 기존에는 프로필 값만 바뀌고 이미 화면에 표시된 번역문은 이전 언어로 남을 수 있었다.

실제 제품에서는 이상한 상태다.

예를 들어 사용자가:

1. English
2. Japanese
3. English

순으로 빠르게 언어를 변경했다고 가정한다.

첫 번째 English 번역과 Japanese 번역이 동시에 진행되고 있다면, 늦게 완료된 Japanese 결과가 다시 English 화면에 들어올 수도 있다.

이를 막기 위해 **translation generation**을 별도로 관리했다.

언어가 바뀌면:

- 기존 remote translated text를 비운다.
- 원문은 유지한다.
- 새로운 target language로 재처리한다.
- 이전 generation에서 뒤늦게 도착한 결과는 publish하지 않는다.

중요한 점은 Firestore의 canonical message 자체는 건드리지 않는 것이다.

서버에는 여전히 다음과 같은 원문 중심 필드만 존재한다.

- messageId
- senderUserId
- originalText
- inputType
- clientTimestamp
- createdAt

번역은 수신자의 로컬 상태다.

이 원칙은 오늘도 유지했다.

## 4. Pagination 상태도 Conversation State의 일부다

과거 메시지를 여러 페이지 불러온 뒤 다른 화면으로 이동했다가 같은 대화로 돌아오면, 이미 불러온 history가 있는데도 pagination cursor가 초기화되어 같은 데이터를 다시 요청할 가능성이 있었다.

이번 작업에서는 같은 conversation으로 다시 진입하는 경우:

- cursor
- initialized state
- exhaustion state
- history availability

를 유지하도록 했다.

반대로 다른 conversation으로 바뀌면 해당 pagination state는 초기화한다.

이것은 작은 UX 개선처럼 보이지만 의미가 크다.

> **현재 conversation은 conversationId 하나가 아니라 현재까지 확보한 history window와 pagination boundary까지 포함하는 session state다.**

## 5. 실패해도 Conversation이 무너지지 않게 만들기

제품에서 중요한 것은 성공 경로뿐만 아니라 실패 경로다.

이번 stabilization에서는 다음 원칙을 유지했다.

- older-history 요청 실패 → 이미 로드된 메시지는 유지
- translation 실패 → 원문은 그대로 표시
- transport 실패 → history와 draft 유지
- send 불가능 → draft를 지우지 않음
- explicit reentry → 필요한 listener 복구
- failed remote translation → 이후 재처리 가능

즉 실패를 상태 초기화로 해결하지 않는다.

가능하면 사용자가 이미 가지고 있던 정보를 보존한다.

Communication Core가 점점 demo가 아니라 product architecture에 가까워지고 있다는 신호라고 생각한다.

---

## 6. TranslationPipeline 종료 이후의 늦은 Callback

ML Kit의 detector, model preparation, translator는 비동기로 동작한다.

문제는 pipeline을 종료한 이후에도 이미 시작된 callback이 돌아올 수 있다는 것이다.

기존 구조에서는 이런 late callback이 종료된 translator를 다시 사용하거나 새로운 작업을 진행할 위험이 있었다.

이번에는 closed 상태를 명시적으로 추가했다.

각 단계가 다음 작업으로 넘어가기 전에:

> **아직 이 pipeline이 살아 있는가?**

를 확인한다.

종료된 pipeline에서는 어떤 late callback도 다음 단계로 진행할 수 없다.

비동기 시스템에서 close는 자원을 닫는 함수 하나가 아니라 **앞으로 들어오는 모든 이벤트의 유효성을 끊는 경계**여야 한다.

## 7. 두 번째 문제: 화면을 떠났더니 읽던 위치를 잃는다

24-E가 끝난 뒤 다음 문제를 다뤘다.

Chat에서 과거 메시지를 읽다가 Friends나 Profile로 이동한 뒤 다시 Chat으로 돌아오면 화면이 최신 메시지로 점프했다.

원인은 명확했다.

ConversationScreen이 composition에서 제거되면서 화면 내부에 remember되어 있던:

- LazyListState
- initialScrollDone
- previousNewestId

가 함께 사라졌다.

다시 화면에 들어오면 초기 LaunchedEffect가 실행되고 무조건 messages.lastIndex로 이동했다.

즉 ViewModel에는 메시지가 살아 있었지만 **사용자가 어디를 읽고 있었는지는 살아 있지 않았다.**

## 8. Index가 아니라 Message ID를 저장한다

처음 생각할 수 있는 해결책은 현재 list index를 저장하는 것이다.

하지만 pagination이 있는 메시지 앱에서는 위험하다.

예를 들어 사용자가 index 20의 메시지를 읽고 있을 때 과거 메시지 50개를 prepend하면 같은 메시지는 더 이상 index 20에 있지 않다.

그래서 viewport anchor를 다음처럼 정의했다.

- authenticated user ID
- conversation ID
- first visible message의 stable message ID
- first-visible pixel offset
- 현재 위치가 newest 근처인지 여부

복원할 때는 저장된 message ID를 현재 message list에서 다시 찾는다.

따라서 history prepend로 index가 바뀌어도 **사용자가 읽던 메시지의 identity는 유지된다.**

## 9. 과거 메시지를 읽는 사용자와 최신 메시지를 보는 사용자는 다르게 처리한다

모든 복귀 상황에서 동일한 scroll 정책을 적용하면 안 된다.

### 과거 history를 읽다가 화면을 떠난 경우

화면 밖에 있는 동안 새 realtime message가 여러 개 들어와도 기존 읽던 위치를 유지한다.

새 메시지가 도착했다는 이유만으로 갑자기 최신 메시지로 보내지 않는다.

### 최신 메시지 근처에서 화면을 떠난 경우

복귀하면 현재 최신 영역으로 이동한다.

즉 단순한 scroll restoration이 아니라 사용자 의도를 보존한다.

> **과거를 읽고 있었다면 과거를 유지한다. 최신을 보고 있었다면 최신을 따라간다.**

## 10. Conversation과 User 사이의 Viewport 격리

Viewport는 conversation ID 하나만으로 저장하지 않았다.

키는:

**userId + conversationId**

이다.

이렇게 해야:

- 사용자 A가 읽던 Conversation X 위치
- 사용자 B가 읽던 Conversation X 위치
- Conversation X와 Conversation Y

가 서로 섞이지 않는다.

이 역시 작은 UI state처럼 보이지만 멀티유저 앱에서는 ownership 문제다.

## 11. Debugging: 실패한 Build도 작업의 일부였다

오늘 build 과정이 처음부터 매끄러웠던 것은 아니다.

첫 테스트는 sandbox 환경에서 Gradle cache lock 파일에 접근할 수 없어 초기화 전에 실패했다.

그다음 incremental Kotlin compiler가 기존 MessageHistory top-level symbol을 resolve하지 못하는 문제가 나타났다.

incremental compilation을 비활성화하기 위해 PowerShell에서 Gradle property를 전달하는 과정에서는 quoting 문제로 잘못된 task로 해석되기도 했다.

그 문제를 수정한 뒤에는 새 JVM test fixture에서 CommunicationMessage의 필수 argument 일부가 빠져 test compilation이 실패했다.

fixture를 수정한 뒤 전체 build를 다시 수행했다.

최종적으로 normal Kotlin settings에서도 다시 build하여 일시적으로 incremental compilation을 끈 상태에서만 우연히 성공한 것이 아님을 확인했다.

> **Build 실패 자체보다 중요한 것은 실패 원인이 production code인지, build environment인지, compiler state인지, test fixture인지 구분하는 것이다.**

## 13. 아직 “검증 완료”라고 말하지 않는 이유

JVM test와 compile verification은 통과했지만 다음은 아직 실제 Android runtime에서 확인하지 않았다.

- 실제 Firebase callback scheduling
- 실제 listener 개수와 cleanup
- 실제 account switch 중 pending callback
- ML Kit download/translation completion timing
- Compose layout measurement
- variable-height translated bubble
- navigation 직전/직후 scroll snapshot timing
- 실제 두 기기 realtime communication
- offline/reconnect

따라서 현재 상태는:

> **코드 수준의 안정화와 isolated state test는 완료했지만, 실제 device acceptance는 남아 있다.**

## 14. 오늘의 Learning

오늘 가장 크게 배운 것은 실시간 communication system에서 **상태의 소유자를 명확하게 정하는 것이 기능 구현보다 중요할 수 있다는 점**이다.

메시지에는 owner가 있다.

번역 작업에도 owner가 있다.

callback에도 generation이 있다.

viewport에도 user와 conversation이라는 owner가 있다.

그리고 lifecycle이 끝났다면 그 이후 도착하는 event는 더 이상 현재 상태를 수정할 권한이 없어야 한다.

오늘 작업 전체는 한 문장으로 정리할 수 있다.

> **Every asynchronous result must prove that it still belongs to the current session.**
