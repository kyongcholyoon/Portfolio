## 1. Lifecycle Became Harder Than the Feature Itself

As the real-time translation messenger grows, one thing is becoming increasingly clear.

Translation itself is not the only difficult problem.

The harder questions now look like this:

- What happens when an old Firebase callback completes after the user signs out?
- What happens when the receiver changes languages A → B → A while translations are still running?
- What happens when pagination and realtime updates arrive together?
- What happens when Chat leaves the Compose tree and later returns?
- What happens when ML Kit finishes after its pipeline has already been closed?
- What happens when state from a previous conversation leaks into the next one?

Each problem looks small in isolation.

Together, they define whether the application behaves like a demo or like a real communication system.

---

## 2. Bringing Auth State Into the ViewModel Lifecycle

ConversationViewModel now owns the Firebase auth-state listener.

When the authenticated account changes, the app does more than replace a user ID.

It invalidates or clears:

- the previous transport listener
- pending conversation operations
- profile callbacks
- pagination work
- translation generations
- account-owned visible messages
- stale account state

The core rule is simple:

> **There is no guarantee that the user who started an asynchronous operation is still the current user when that operation finishes.**

Callbacks therefore verify their original authentication generation and UID before publishing results.

In an asynchronous app, receiving a callback is less important than proving that the callback is still valid.

---

## 3. Receiver-language Refresh Is Not Just a Preference Change

Changing preferredLanguage used to update the profile value while already-loaded translated bubbles could remain in the old language.

That becomes dangerous during rapid transitions such as:

1. English
2. Japanese
3. English

If multiple translation tasks are still running, an old Japanese result could finish late and overwrite the current English UI.

The solution was a separate **translation generation**.

When the receiver language changes:

- old derived translations are cleared
- original message content remains unchanged
- loaded remote originals are reprocessed for the new target
- results from older translation generations are rejected

The canonical Firestore message remains original-only.

The server stores the source message, while translation remains a receiver-side artifact.

---

## 4. Pagination Is Part of Conversation State

A conversation is more than a conversation ID.

After older pages have been loaded, the active session also owns:

- the pagination cursor
- initialization state
- exhaustion state
- history availability

Same-conversation reentry now preserves those values.

Switching to a different conversation resets them.

> **The current conversation is a session state that includes the loaded history window and pagination boundary, not just a conversationId.**

---

## 5. Recoverable Failure Should Preserve Useful State

Another principle reinforced today was that recoverable failures should not destroy information the user already has.

Examples:

- older-history failure keeps loaded messages
- translation failure keeps the original text visible
- transport failure keeps history and the draft
- a rejected send does not clear the composer
- explicit reentry can recover the listener
- failed remote translations remain eligible for retry

Failure recovery is becoming part of the architecture rather than an afterthought.

---

## 6. Closing TranslationPipeline Properly

ML Kit detectors, model preparation, and translators are asynchronous.

A callback can complete after the pipeline that started it has already been disposed.

A closed state was added to TranslationPipeline.

Before any late callback advances to the next step, the pipeline verifies that it is still alive.

Closing a pipeline therefore means more than releasing a resource.

> **It revokes the right of future asynchronous events to mutate the current state.**

---

## 7. The Next Problem: Losing the Reading Position

After 24-E stabilization, the next issue was UI continuity.

If the user was reading older messages, navigated to Friends or Profile, and returned to Chat, the list jumped to the newest message.

The messages themselves were still alive in the Activity-owned ViewModel.

The reading position was not.

The reason was screen-local state:

- LazyListState
- initialScrollDone
- previousNewestId

When ConversationScreen left composition, that transient state disappeared.

On reentry, the initial effect scrolled directly to the latest message.

The ViewModel remembered the conversation.

The UI did not remember **where the user had been reading**.

---

## 8. Stable Message IDs Instead of List Indices

Saving the current list index would not survive pagination.

If older history is prepended, every later index moves.

The viewport is now represented by:

- authenticated user ID
- conversation ID
- first visible stable message ID
- first-visible pixel offset
- whether the user was at or near the newest message

On restoration, the saved message ID is resolved against the current message list.

The index may have changed.

The identity of the message has not.

---

## 9. Preserving User Intent

There are two different restoration behaviors.

### Reading older history

If the user leaves while reading older messages, new realtime messages received while away must not force a jump to the bottom.

The saved message anchor is restored.

### Already near the newest message

If the user was already near the bottom, returning should show the current newest area, including messages that arrived while away.

This is not simply scroll persistence.

> **If the user was reading the past, preserve the past. If the user was following the present, follow the present.**

---

## 10. Viewport Isolation by User and Conversation

Viewport state is keyed by:

**userId + conversationId**

Conversation A cannot inherit Conversation B's reading position.

Another authenticated user cannot inherit the previous user's viewport either.

Even UI state needs ownership in a multi-user application.

## 11. Debugging: Failed Builds Were Part of the Work

The build process was not clean from the first attempt.

Problems included:

- sandbox access failure on a Gradle cache lock
- a temporary incremental Kotlin symbol-resolution failure
- incorrect PowerShell quoting for a Gradle property
- missing required CommunicationMessage constructor arguments in a new JVM test fixture

Each failure was classified separately as a product-code, environment, compiler-state, or test-fixture issue.

After fixing the actual fixture problem, the complete build passed.

The project was then rebuilt again under normal Kotlin compiler settings to ensure success did not depend on a temporary workaround.

> **A failed build is not a diagnosis. First identify which layer actually failed.**

## 13. What Is Not Yet Proven

Passing JVM and compilation tests does not mean runtime work is finished.

Still pending on real devices:

- actual Firebase callback scheduling
- listener ownership and cleanup
- authentication changes during pending work
- ML Kit model-download and completion timing
- Compose measurement timing
- variable-height translated bubbles
- navigation/disposal timing
- offline and reconnect behavior
- two-device realtime behavior

The current status is:

> **Architecture and isolated state behavior are validated in code and tests; real-device runtime acceptance is still required.**

---

## 14. Learning

Today's work can be summarized by one principle:

> **Every asynchronous result must prove that it still belongs to the current session.**

Messages have owners.

Translation work has owners.

Callbacks have generations.

Viewport state has a user and a conversation.

When a lifecycle ends, events that arrive afterward should no longer have authority over the current state.

That principle is becoming one of the foundations of the Communication Core.
