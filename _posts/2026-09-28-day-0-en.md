> **Day 0 is not a record of finished implementation. It documents the period when I decided what to build and defined the direction of the first prototype. The early concept differs substantially from the current architecture.**

## Starting a portfolio with "why" rather than only "what"

Before beginning full implementation, I first explored several ideas for my personal engineering portfolio.

The goal was not to create another small demo that simply worked. I wanted a project that could connect the subjects I was studying—**NPU, Edge AI, and model optimization**—to a real user problem, while also demonstrating mobile development, embedded systems, communication, and AI.

Several candidates were considered. One representative idea preserved in the original design discussions was a **self-learning piano, organ, and harmony education system**. It would combine manuals and pedal keyboards, MIDI input, real-time harmony analysis, and educational content. It was an interesting project, but I chose a different idea as the first one to build.

The project I selected first was what I then called a **real-time on-device translation system for deaf and hard-of-hearing users**.

## Why this project became priority #1

This project could connect multiple engineering problems rather than demonstrating only one technology.

- Real-time translation across language barriers
- Accessibility for deaf and hard-of-hearing users
- A smartphone-based mobile application
- BLE wearable input
- Smart-glasses visual output
- STT and TTS
- Offline operation
- Opportunities for Edge AI and model optimization

More importantly, it was not a project created simply to showcase technologies. It had a clear user problem: **helping people communicate without constantly breaking eye contact during a face-to-face conversation**.

The initial question was simple:

> Can two people continue looking at each other and communicate naturally even when they speak different languages or when one of them cannot rely on hearing?

That question eventually became the central axis of the entire project.

## The input/output model of the first prototype

The early concept assigned different input and output devices depending on the user's role.

### Deaf or hard-of-hearing user

- **Input:** a wireless thigh-mounted keyboard
- **Output:** subtitles on smart glasses
- **Secondary output:** smartphone display

### General user

- **Input:** speech captured by the smartphone microphone
- **Output:** smartphone display and speaker
- **Processing:** STT → translation → TTS

The most important UX principle was **Eyes-free Input / Eyes-up Output**.

If a deaf user has to look down at a smartphone while typing, maintaining eye contact becomes difficult. The concept was therefore to keep the hands on a thigh-mounted keyboard, keep the eyes on the conversation partner, and read the partner's speech through smart glasses.

A significant part of this idea survived even after the scope of the project expanded.

## Sign-language input was considered, then removed

The early concept also explored recognizing sign language through a camera and translating it into another spoken language.

As the prototype became more concrete, I removed that path.

Sign-language recognition introduces a large independent problem space: camera input, hand and body pose tracking, language-specific sign systems, and real-time recognition accuracy. A thigh-mounted keyboard, on the other hand, allows the user to enter the intended text precisely while relying on the mature BLE HID standard.

For the first prototype, I therefore **removed sign-language recognition and simplified the input path around text**.

This was not merely feature reduction. It was scope control so that the core user experience could be validated first.

## The biggest early technical assumption: a custom lightweight translation model

The translation engine is the part that changed most dramatically from the first design.

My early plan centered on converting an open-source translation model to ONNX, applying INT8 quantization, and running inference directly on a smartphone NPU. NLLB- and Gemma-family models were considered as candidates, with the goal of a low-latency translation pipeline that could operate without a network connection.

The reasoning at the time was straightforward:

**Edge AI course → model optimization → NPU → offline translation**

Later, however, the assumption changed significantly as I examined and implemented the actual Android product architecture.

For a solo project, it is difficult to build a general-purpose lightweight translation model that exceeds mature commercial engines in both quality and multilingual coverage. Sacrificing product quality simply to say that the model was custom-built would not be a good engineering decision.

The current project therefore uses **Google ML Kit On-device Translation** as the default local translation engine, with optional Cloud AI when higher-quality contextual translation is desired.

Edge AI and NPU work have moved toward areas where offline and low-latency inference have a clearer product reason, such as **speech enhancement and environmental sound awareness**, rather than forcing a custom model into the translation path.

This does not mean the original design was a failure. A prototype should **expose assumptions so that implementation can replace them with better decisions**.

## The scope of the project also changed

The original concept was centered on real-time translation for deaf and hard-of-hearing users.

While continuing to examine the input/output model, I realized that the underlying problem was broader.

If the system can accept multiple inputs—smartphone keyboard, voice, or a wearable keyboard—and deliver the result through multiple outputs—smartphone UI, speaker, smart glasses, or haptics—it no longer has to be limited to a single accessibility category.

The current direction of the project is summarized by one line:

> **Any Input. Any Output. Any Language. One Conversation.**

Today, the goal is an **All-in-One Communication Solution** that reduces both language and hearing barriers.

I do not want to rewrite Day 0 as though this conclusion had been obvious from the beginning. The current direction emerged gradually through repeated discussion, implementation, and architectural revision.

## The first lesson from Day 0

The code from this period was still far from the current product architecture, and many technical assumptions would later change.

But one principle became clear.

**A strong engineering portfolio should not be a list of technology names. It should show the problem being solved and the reasoning behind the technology choices.**

I should not invent a problem in order to use an NPU. I should use an NPU when the problem genuinely benefits from it.  
I should not add AI simply to claim that the product contains AI. I should use AI where it actually improves the user experience.

That principle became the standard I used when changing the architecture later.

Rather than continuing the prototype code unchanged, I began reconsidering the system around a real Android product: the translation engine, communication architecture, user model, and real-time messaging were each tested step by step.
