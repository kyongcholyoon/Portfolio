> **The key decision on Day 3 was: do not pre-configure the other person's language. Messages should be sent as originals, while the receiving device detects the source language and translates into the recipient's preferredLanguage.**

## Problem: a sender should not have to know the recipient's language

By Day 2, I had verified that on-device translation itself worked on Android.

The next problem was no longer translation quality. It was the **conversation architecture**.

If I am a Korean-speaking user and my friend speaks Japanese, the sender could translate into Japanese before transmission.

That looks simple at first, but it does not scale well.

- A user may speak multiple languages.
- The same user may change their preferred language depending on context.
- A group conversation may require several translations for one message.
- If senders manage recipient language settings, the user model and messaging layer become tightly coupled.

So I changed the model.

**The sender owns the original message. The receiver owns translation.**

## UserProfile: users choose only their own language

I introduced **preferredLanguage** into the user profile.

The initial default was English, while users could change it to their own preferred language.

The important design choice was what not to store: I did not want a friend profile to contain rules such as “always translate messages for this person into Japanese.”

The sender sends the original.

The receiver then:

1. receives the original message
2. detects its source language
3. compares it with the receiver's preferredLanguage
4. translates locally when necessary
5. displays both original and translation

With this model, changing one user's preferredLanguage does not change how other users store or transmit messages.

## The original becomes canonical data

This was more than a UI decision. It changed the direction of the data model.

The **original text is canonical message data**.

A translation is derived data that depends on the receiver's settings and environment.

That separation provides several advantages:

- the original remains intact when language preferences change
- the same message can be translated again into another language
- translation engines can be replaced without losing the source
- optional Cloud AI can be added without changing the canonical message schema
- future group conversations can distribute one original and let each recipient translate locally

This decision later becomes a core assumption of the Firebase message model.

## Separating sender and receiver processing

The message flow became conceptually clearer:

**Sender**  
Input → Outgoing message → Transport

**Receiver**  
Incoming message → Language detection → Translation → Conversation UI

To represent that separation in code, I moved toward structures such as **IncomingMessage**, **IncomingMessageProcessor**, and **UserProfile**.

The UI should not need to know the other person's language or construct translation pairs itself. The receiver-side processing layer should make that decision from preferredLanguage.

## UI rule: original first, translation directly below

If a translation product hides the source text, users lose an important way to verify what was actually said.

So I defined the bubble order explicitly:

1. **Original**
2. **Translation**
3. **Language direction**

For example:

**こんにちは。今日はどうですか。**  
안녕하세요. 오늘 어떠세요?  
JA → KO

The original remains the primary information, while the translation stays immediately readable.

I kept this rule in later messaging UI work.

## Different responsibilities for ME and REMOTE messages

A message I wrote is already my original text.

If the receiver pipeline also re-detects and re-translates my own message, it creates redundant work and confusing UI state.

So the direction became:

- **ME messages** — preserve the original
- **REMOTE messages** — translate according to the receiver's preferredLanguage

This distinction later becomes useful when Firestore listeners deliver a user's own sent message back to the same client and duplicate bubbles must be avoided.

## Emulator instability and a shift toward real-device testing

I also hit a practical development problem on Day 3.

The Android emulator repeatedly became unstable, including **System UI isn't responding** and long startup timeouts.

Given the development PC and emulator overhead, relying on emulators for every critical verification step was becoming inefficient.

I therefore decided that later communication and translation testing should make greater use of real Android devices.

This was not an architectural feature, but it was a real engineering constraint that affected development speed.

## Verification

Key decisions and structures confirmed on Day 3:

- introduced **preferredLanguage**
- avoided pre-configuring a friend's language
- sender transmits the original
- receiver detects the source language
- receiver translates into its own preferredLanguage
- original text remains canonical message data
- receiver processing moves into IncomingMessage / IncomingMessageProcessor
- UI order is original → translation → language direction
- ME and REMOTE messages have different processing responsibilities
- emulator instability pushed later verification toward real devices

The main outcome of the day was not a large networking feature. It was deciding **who owns translation**, a decision that would shape the entire messaging system.

## What I Learned

At first, “how should I translate this?” looked like the hardest problem.

In a real product, a more fundamental question comes first:

> **Who should be responsible for translation?**

Separating original messages from translations made the architecture much simpler.

Messages can remain stable, while translations are generated according to the recipient's current needs.

That makes the system more resilient to new languages, new translation engines, and future conversation types.

## Next

The next step is to leave the purely local message demo behind.

I need a **Transport abstraction** that can:

- validate the send/receive pipeline using local loopback
- later expand to real smartphone-to-smartphone internet messaging

At the same time, the boundary must stay clear: personal peripherals such as the keyboard and smart glasses use BLE, while remote user-to-user communication uses the internet.
