## ポートフォリオを「何を作ったか」ではなく「なぜ作ったか」から始める

本格的な実装に入る前に、まず個人ポートフォリオとしてどのようなプロジェクトを作るか、複数のアイデアを検討した。

目標は、単に機能するサンプルを一つ作ることではなかった。授業で扱う **NPU、Edge AI、モデル軽量化**を実際のユーザー課題と結び付けながら、モバイル、組み込み、通信、AI を同時に示せるプロジェクトが必要だった。

当時はいくつかの候補を比較した。対話記録に残っている代表的な候補の一つが、**ピアノ・オルガンの独学と和声学教育システム**だった。手鍵盤と足鍵盤、MIDI 入力、リアルタイムの和声分析、教育コンテンツを組み合わせるアイデアである。魅力的なテーマではあったが、最初のプロジェクトには別の案を選んだ。

最初に開発することにしたのは、当時 **聴覚障害者向けリアルタイム・オンデバイス通訳翻訳プロジェクト**と呼んでいたアイデアだった。

## なぜこのプロジェクトを最優先にしたのか

このプロジェクトは、一つの技術だけを見せるデモではなく、複数の課題を同時に結び付けることができた。

- 言語の壁を下げるリアルタイム翻訳
- 聴覚障害者のためのアクセシビリティ
- スマートフォンベースのモバイルアプリ
- BLE ベースのウェアラブル入力デバイス
- スマートグラスによる視覚出力
- STT と TTS
- オフライン動作
- Edge AI とモデル軽量化の可能性

何より重要だったのは、技術を並べるためのプロジェクトではなく、**実際の会話で相手から視線を外さずにコミュニケーションできるようにするという明確なユーザー課題**があったことだ。

初期の中心的な問いはシンプルだった。

> 言語が違う、あるいは一方が音を聞きにくい状況でも、二人が互いの顔を見ながら自然に会話できるだろうか。

この問いが、その後のプロジェクト全体の中心軸になった。

## 初期プロトタイプで定めた入出力構成

初期構想では、ユーザーの役割に応じて入出力デバイスを分けていた。

### 聴覚障害ユーザー

- **入力:** 太ももに装着するワイヤレスキーボード
- **出力:** スマートグラス上の字幕
- **補助出力:** スマートフォン画面

### 一般ユーザー

- **入力:** スマートフォンのマイクによる音声
- **出力:** スマートフォン画面とスピーカー
- **処理:** STT → 翻訳 → TTS

この構成で最も重要な UX 原則は **Eyes-free Input / Eyes-up Output** だった。

聴覚障害ユーザーがスマートフォン画面を見下ろしながら入力すると、相手と視線を合わせにくい。そこで、手は太ももキーボードに置き、目は相手を見たまま、相手の発話をスマートグラスで読む形を考えた。

このアイデアは、後にプロジェクトの範囲が大きく広がった後も、かなりの部分が残っている。

## 当初は手話入力も検討した

初期アイデアでは、手話をカメラで認識して外国語へ翻訳する方向も検討した。

しかし、プロトタイプを具体化する過程でこの経路は外した。

手話認識には、カメラ入力、手や身体の姿勢推定、言語ごとの手話体系、リアルタイム認識精度など、独立した大きな問題領域が生まれる。一方、太ももキーボードなら、ユーザーは伝えたい文章を正確に入力でき、BLE HID という成熟した技術も利用できる。

そのため、最初のプロトタイプでは **手話認識を外し、テキスト入力中心に単純化**した。

これは単に機能を減らしたのではなく、中心となるユーザー体験を先に検証するためのスコープ調整だった。

## 当時最大の技術的仮説：独自の軽量翻訳モデル

初期設計から最も大きく変わった部分は翻訳エンジンである。

当時は、オープンソースの翻訳モデルを ONNX ベースへ変換し、INT8 量子化を施してスマートフォンの NPU で直接推論する構成を中心に考えていた。NLLB や Gemma 系モデルを候補として検討し、ネットワークなしで動作する超低遅延翻訳システムを想定していた。

当時の発想は自然だった。

**Edge AI の授業 → モデル軽量化 → NPU → オフライン翻訳**

しかし、その後、実際の Android 製品構造を検討して実装していく中で、この仮説は大きく変わった。

汎用翻訳の品質と多言語対応を、個人プロジェクト規模の独自軽量モデルで商用エンジン以上にするのは難しい。製品品質を犠牲にしてまで「自作モデル」を入れることは、良いエンジニアリング判断ではないと考えた。

現在のプロジェクトでは **Google ML Kit On-device Translation** を標準のローカル翻訳エンジンとして使い、必要に応じて Cloud AI を選択的に利用する構成へ進化している。

Edge AI と NPU は翻訳そのものより、**音声強調や環境音認識のように、オフラインかつ低遅延処理が本当に必要な領域**へ適用する方向に移った。

<div class="architecture-evolution">

**Early Prototype**

Custom translation model  
→ ONNX  
→ INT8 quantization  
→ NPU inference  
→ translated output

**Current Direction**

Input  
→ Smartphone Communication Core  
→ ML Kit on-device translation / optional Cloud AI  
→ Phone / Smart Glasses / Watch output

Edge AI / NPU  
→ speech enhancement and environmental sound awareness

</div>

この変化は、初期設計が失敗だったという意味ではない。むしろプロトタイプの役割は、**仮説を表面化させ、実装を通してより良い選択へ置き換えること**だと考えている。

## プロジェクトの範囲も変わった

最初は聴覚障害者を中心としたリアルタイム翻訳システムだった。

しかし、入出力構造を検討し続ける中で、問題の範囲はもっと広いと気付いた。

スマートフォンキーボード、音声、ウェアラブルキーボードなど複数の入力を受け取り、スマートフォン UI、スピーカー、スマートグラス、ハプティクスなど複数の出力へ渡せるなら、この構造は特定の障害だけを対象としたアプリに限定されない。

現在のプロジェクトの方向性は、次の一文で表している。

> **Any Input. Any Output. Any Language. One Conversation.**

つまり現在は、**言語と聴覚の壁を同時に下げる All-in-One Communication Solution**を目指している。

ただし、Day 0 の時点ですでにこの結論を知っていたかのようには書きたくない。この方向性は、初期プロトタイプから始まり、実装と議論を繰り返しながら生まれた結果である。

## Day 0 で得た最初の教訓

この日のコードは、まだ現在の製品レベルとは大きく離れていた。技術的な仮説も後にかなり変更された。

それでも、一つだけ明確になった。

**良いポートフォリオは技術名の一覧ではなく、解決したい問題と技術選定の理由を示すべきだ。**

NPU を使うために問題を作るのではなく、問題が NPU を必要とするときに使う。  
AI を入れるために機能を作るのではなく、AI がユーザー体験を本当に改善するときに使う。

この原則は、その後アーキテクチャを何度も変更する際の判断基準になった。

## 次のステップ

Day 0 がアイデアと仮説を整理した日だとすれば、次の段階から実際の実装が始まる。

プロトタイプのコードをそのまま育てるのではなく、現在の Android 製品に合う構造を改めて検討し、翻訳エンジン、通信構造、ユーザーモデル、リアルタイムメッセージングを一つずつ実機で検証し始めた。

次の記事では、**アイデア段階のプロトタイプから実際の Android 製品アーキテクチャへ移行する過程**を記録する。
