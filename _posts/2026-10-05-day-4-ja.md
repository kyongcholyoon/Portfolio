> **Day 4 では、翻訳パイプラインを実際のメッセージング構造へ拡張し始めた。まず MessageTransport と LocalLoopbackTransport で送受信の境界を作り、その後、遠隔スマートフォン間は Internet/Firebase、個人周辺機器は BLE という物理的な境界を明確にした。**

## 目標：「翻訳できるアプリ」から「メッセージを交換するシステム」へ

Day 3 までに、原文と翻訳の責任を分離した。

送信者は原文を作り、受信者は自分の preferredLanguage を基準に翻訳する。

次に必要だったのは、その原文を実際に **どう届けるか** だった。

UI 内で直接関数を呼び、相手から届いたように見せるだけでは、本物のネットワーク製品へ拡張しにくい。

そこでメッセージ配送そのものを一つの境界として切り離した。

## MessageTransport

送受信コードを特定のネットワーク技術へ直接結び付けないために **MessageTransport** という契約を作った。

概念的には、UI と翻訳パイプラインは transport の具体的な実装を知らなくてよい。

**OutgoingMessage → MessageTransport → IncomingMessage → IncomingMessageProcessor**

この形なら transport は後から差し替えられる。

- 開発中：LocalLoopbackTransport
- 実ユーザー間通信：FirebaseMessageTransport
- 将来別 backend が必要なら別実装

目的は「Firebase アプリ」を作ることではなく、**communication system** を作ることだからだ。

Firebase は現在の transport 実装の一つに過ぎず、UI や翻訳の中心に置くべきではない。

## LocalLoopbackTransport で先に検証

実ネットワークを接続する前に **LocalLoopbackTransport** を作った。

自分が入力した原文を transport が相手から送られたメッセージのように返し、そのメッセージが IncomingMessageProcessor を通って言語検出と翻訳まで進む構造だ。

この過程で message ID が衝突し、ME メッセージと REMOTE メッセージが同一メッセージとして扱われる問題が起きた。

loopback 側に送信メッセージとは異なる安定した ID を与えるよう修正し、

**ME 原文 → transport → REMOTE 受信 → 言語検出 → 受信側翻訳 → UI**

の流れが正常に動作することを確認した。

ネットワークを使わず messaging boundary 全体を先に検証できる点が loopback の利点だった。

## Bluetooth と Internet の境界を明確にする

このプロジェクトには Bluetooth と Internet の両方が登場する。

初期段階では、これらが一つの通信問題のように混ざって見える可能性があった。

しかし役割を分けると明確になる。

### BLE / Bluetooth

一人のユーザーの個人周辺機器：

- 太ももキーボード → スマートフォン
- スマートフォン → スマートグラス

つまり **personal device network** である。

### Internet

離れたユーザー同士：

- Smartphone A ↔ Smartphone B
- 会話メッセージ
- 友人関係
- conversation

つまり **user-to-user communication network** である。

この境界を明確にしたことで、「二台のスマートフォンも Bluetooth でつなぐべきか」といった不要な複雑さを取り除いた。

遠隔ユーザー通信はインターネット、BLE はユーザーの周辺機器に集中させる。

## Firebase を実 backend 候補として接続し始める

遠隔 transport には **Firebase Authentication + Cloud Firestore** を選んだ。

初期設定で行ったこと：

- Firebase project の接続
- Android アプリの Firebase 設定
- Anonymous Authentication の有効化
- 匿名ログイン後の UID 確認
- Cloud Firestore 作成
- Firestore write テスト
- セキュリティルールと conversation 構造の検討

Anonymous Auth を先に使った理由は、登録 UI に時間を使わず、各アプリインスタンスに安定した user identity を与え、メッセージングを検証できるからだ。

本格的なアカウントシステムは後で拡張できるが、transport 開発にはまず UID が必要だった。

## Firestore には何を送るか

Day 3 で決めた原則をそのまま維持した。

**ネットワークで送る canonical message は原文である。**

翻訳結果をサーバーへ保存して相手へ送るのではない。

受信端末が自分の言語設定とローカル翻訳エンジンを基準に処理する。

当時の目標フローは次の通り。

**Phone A**  
原文作成  
→ Firestore 送信

**Phone B**  
原文受信  
→ LanguageDetector  
→ ML Kit on-device translation  
→ 原文 + 翻訳文表示

この構造は privacy と offline fallback の面でも有利だ。サーバーが全ユーザーの全翻訳組み合わせを生成する必要がない。

## この日はどこまで進んだか

Day 4 では LocalLoopbackTransport と受信側翻訳パイプラインを実際に検証した。

Firebase 側は Auth と Firestore の基本接続、UID 確認、write テストまで進めた。

ただし **FirebaseMessageTransport 全体を完成させ、二台の端末間でリアルタイム messaging を検証する作業は次の開発段階に残した。**

この区別は重要だ。

Firebase project が接続できたことと、user-to-user realtime messaging が完成したことは同じではない。

## Verification

実際に確認した内容：

- MessageTransport abstraction
- LocalLoopbackTransport 実装
- loopback message ID 衝突の発見と修正
- ME 原文 → REMOTE 受信 → receiver-side 翻訳フロー
- 個人周辺機器 BLE / 遠隔ユーザー Internet の境界確定
- Firebase Anonymous Auth 接続
- 匿名ユーザー UID 発行確認
- Cloud Firestore 接続と write テスト
- Firestore には原文を渡す canonical-message 原則を維持

未完了：

- FirebaseMessageTransport の完成
- 二つの Android インスタンス間の bidirectional realtime messaging
- conversation 単位のメッセージ分離
- participant 権限検証
- listener lifecycle の検証

## What I Learned

一つの機能を直接実装すること以上に、**どこに境界を置くか** がシステムの拡張性へ大きく影響する。

MessageTransport を作ると、UI、翻訳、ネットワークを独立して考えられるようになった。

また Bluetooth と Internet の役割を分けることで、ハードウェアと server architecture もかなり単純になった。

> **キーボードとメガネはユーザーの周辺機器。相手ユーザーはインターネットの向こう側にいる participant。**

この一文が、その後の通信設計の基準になった。
