> **Day 3의 핵심 결정은 “상대방 언어를 미리 설정하지 않는다”였다. 메시지는 원문으로 보내고, 수신 기기가 원문 언어를 감지한 뒤 수신자의 preferredLanguage로 번역하도록 구조를 바꿨다.**

## 문제: 송신자가 상대 언어를 알아야 하는 구조는 확장되지 않는다

Day 2까지는 온디바이스 번역 자체가 실제 Android에서 동작한다는 것을 확인했다.

그 다음부터는 번역 품질보다 **대화 구조**가 문제였다.

만약 내가 한국어 사용자이고 친구가 일본어 사용자라면, 송신 앱이 “이 친구는 일본어를 쓴다”는 정보를 알고 번역해 보내는 구조를 만들 수도 있다.

하지만 사용자가 늘어나면 문제가 생긴다.

- 상대가 여러 언어를 사용할 수 있다.
- 같은 사람도 상황에 따라 preferred language를 바꿀 수 있다.
- 단체 대화에서는 한 메시지를 여러 언어로 따로 만들어야 할 수도 있다.
- 송신자가 상대방의 언어 설정을 책임지는 구조는 사용자 모델과 메시징이 강하게 결합된다.

그래서 방향을 바꿨다.

**송신자는 원문만 책임지고, 번역은 수신자가 책임진다.**

## UserProfile: 내가 선택하는 것은 내 언어뿐

사용자 프로필에는 **preferredLanguage**를 둔다.

기본값은 영어로 두되, 사용자가 자신의 언어를 바꿀 수 있게 한다.

중요한 점은 친구 프로필에 “이 사람에게는 무조건 일본어로 보내라” 같은 상대 언어 설정을 두지 않는 것이다.

송신 측은 원문을 보낸다.

수신 측은:

1. 원문을 받는다.
2. 원문 언어를 자동 감지한다.
3. 자신의 preferredLanguage와 비교한다.
4. 필요하면 로컬에서 번역한다.
5. 원문과 번역문을 함께 보여준다.

이 구조라면 한 사람이 preferredLanguage를 바꿔도 다른 사용자의 메시지 저장 방식은 바뀌지 않는다.

## 원문이 canonical data가 된다

이 결정은 단순한 UI 변경이 아니라 데이터 모델의 방향을 바꿨다.

메시지의 canonical data는 **원문**이다.

번역 결과는 수신자의 환경과 설정에 따라 달라지는 derived data다.

이 구분을 하면 여러 장점이 생긴다.

- 상대방이 언어 설정을 바꿔도 원문은 그대로 남는다.
- 같은 메시지를 여러 언어로 다시 번역할 수 있다.
- 번역 엔진을 교체해도 메시지 원본을 잃지 않는다.
- Cloud AI를 선택적으로 추가해도 원문 데이터 모델은 바뀌지 않는다.
- 이후 group conversation으로 확장할 때도 한 개의 원문을 각 수신자가 자기 언어로 처리할 수 있다.

이날의 설계는 이후 Firebase 메시지 구조의 중요한 전제가 된다.

## IncomingMessageProcessor로 송신과 수신을 분리

메시지 처리 흐름도 분리했다.

개념적으로는 다음과 같다.

**Sender**
Input → Outgoing message → Transport

**Receiver**
Incoming message → Language detection → Translation → Conversation UI

이 책임을 코드에서도 분명하게 하기 위해 **IncomingMessage**, **IncomingMessageProcessor**, **UserProfile** 같은 구조를 도입하는 방향으로 정리했다.

UI가 “상대 언어가 무엇인지”를 들고 번역 pair를 직접 조합하는 구조를 피하고, 수신 처리 단계가 preferredLanguage를 기준으로 번역을 결정하게 했다.

## UI 원칙: 원문 먼저, 번역문은 그 아래

번역 제품에서 원문을 숨기면 사용자는 번역 결과를 검증하기 어렵다.

그래서 말풍선의 표시 순서를 명확하게 정했다.

1. **원문**
2. **번역문**
3. **언어 방향**

예를 들면:

**こんにちは。今日はどうですか。**  
안녕하세요. 오늘 어떠세요?  
JA → KO

이 순서를 채택한 이유는 원문을 primary information으로 보존하면서도, 번역문을 바로 읽을 수 있게 하기 위해서다.

이 원칙은 이후 메시지 UI에서도 유지한다.

## 자기 메시지와 상대 메시지의 처리 차이

내가 보낸 메시지는 이미 내가 작성한 원문이다.

따라서 수신 파이프라인에서 자기 메시지까지 다시 감지하고 번역하면 중복 처리와 UI 혼란이 생길 수 있다.

그래서 **ME 메시지는 원문 중심**, **REMOTE 메시지는 수신자의 preferredLanguage에 따라 번역**하는 방향을 잡았다.

이 구분은 나중에 Firebase listener가 자기 메시지를 다시 수신했을 때 중복 버블을 막는 문제와도 연결된다.

## 에뮬레이터 문제와 실기기 테스트 방향

이날 개발 중 Android 에뮬레이터가 안정적으로 동작하지 않는 문제도 겪었다.

**System UI isn't responding**과 긴 startup timeout이 반복되면서, 모든 검증을 에뮬레이터에만 의존하는 것이 비효율적이라는 판단을 했다.

개발 PC 사양과 emulator overhead를 고려해, 이후 중요한 통신·번역 검증은 실제 Android 기기도 적극 활용하는 방향으로 전환했다.

이것은 기능 설계와 별개지만, 실제 개발 속도에 영향을 주는 현실적인 문제였다.

## Verification

Day 3에서 확정하거나 코드 구조에 반영한 핵심 사항:

- 사용자에 **preferredLanguage** 개념 도입
- 친구에게 상대 언어를 미리 지정하지 않는 방향
- 송신자는 원문을 전달
- 수신자가 원문 언어 자동 감지
- 수신자의 preferredLanguage로 온디바이스 번역
- 원문을 canonical message data로 유지
- IncomingMessage / IncomingMessageProcessor로 수신 처리 책임 분리
- UI는 원문 → 번역문 → 언어 방향 순서
- ME와 REMOTE 메시지의 처리 책임 분리
- emulator 불안정으로 이후 real-device 검증 비중 확대

이날의 핵심은 대규모 네트워크 기능 구현보다, 이후 메시징 시스템 전체를 지탱할 **translation ownership**을 결정한 것이었다.

## What I Learned

처음에는 “어떻게 번역할 것인가”가 가장 어려운 문제처럼 보였다.

하지만 실제 제품 구조에서는 그보다 먼저,

> **누가 번역을 책임져야 하는가?**

를 정해야 했다.

원문과 번역을 분리하자 구조가 단순해졌다.

메시지는 메시지대로 보존하고, 번역은 수신자의 현재 상황에 맞춰 생성한다.

이 원칙 덕분에 언어 수가 늘어나거나 번역 엔진이 바뀌어도 메시징 핵심 구조를 유지할 수 있게 됐다.
