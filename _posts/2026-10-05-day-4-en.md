> **On Day 4, I started extending the translation pipeline into a real messaging architecture. I first created MessageTransport and LocalLoopbackTransport to define the send/receive boundary, then clarified a physical architecture rule: remote smartphone-to-smartphone communication uses the Internet/Firebase, while personal peripherals use BLE.**

## Goal: move from “an app that translates” to “a system that exchanges messages”

By Day 3, the responsibility split was clear.

The sender owns the original message.  
The receiver translates according to its own preferredLanguage.

The next question was how to actually **deliver that original message**.

A UI that directly calls local functions and pretends a remote message arrived is not enough for a real communication product.

So I separated message delivery behind its own boundary.

## MessageTransport

I introduced **MessageTransport** so the send/receive path would not be tightly coupled to one network technology.

Conceptually, the UI and translation pipeline should not need to know which transport implementation is being used.

**OutgoingMessage → MessageTransport → IncomingMessage → IncomingMessageProcessor**

That gives the system replaceable transport implementations:

- during development: LocalLoopbackTransport
- real user-to-user communication: FirebaseMessageTransport
- future backend changes: another implementation

The goal is not to build a “Firebase app.”

The goal is to build a **communication system**, with Firebase as one transport implementation rather than the center of the architecture.

## Validate with LocalLoopbackTransport first

Before adding a real network, I built **LocalLoopbackTransport**.

It takes a message I send and returns it as though it came from a remote participant. That returned message then passes through IncomingMessageProcessor, language detection, and receiver-side translation.

During this work, I found an ID collision: the ME message and the simulated REMOTE message could be treated as the same message.

I fixed the loopback side so that the simulated remote message receives its own stable identity.

After that, the full local path worked:

**ME original → transport → REMOTE receive → language detection → receiver-side translation → UI**

Loopback was useful because I could verify the entire messaging boundary without introducing network uncertainty yet.

## Clarifying the Bluetooth / Internet boundary

This project uses both Bluetooth and the Internet.

At first, those could easily be mixed together as one broad “communication problem.”

The roles become much clearer when separated.

### BLE / Bluetooth

Personal peripherals belonging to one user:

- thigh-mounted keyboard → smartphone
- smartphone → smart glasses

This is the **personal device network**.

### Internet

Communication between remote users:

- Smartphone A ↔ Smartphone B
- conversation messages
- friend relationships
- conversation state

This is the **user-to-user communication network**.

Defining this boundary removed unnecessary questions such as whether two users' phones should also connect directly over Bluetooth.

Remote users communicate over the Internet. BLE stays focused on a user's own peripherals.

## Starting the Firebase backend path

For the remote transport, I chose **Firebase Authentication + Cloud Firestore**.

The initial setup work included:

- connecting the Firebase project
- configuring the Android app
- enabling Anonymous Authentication
- signing in anonymously and confirming a UID
- creating Cloud Firestore
- testing a Firestore write
- reviewing security rules and conversation structure

Anonymous Auth was useful because it provided stable user identity without spending development time on account-registration UI first.

A richer account system can come later. Transport development needed reliable UIDs immediately.

## What should be stored in Firestore?

I kept the rule from Day 3:

**The canonical network message is the original text.**

The server does not need to store every translated variant and send a pre-translated message to each recipient.

Instead, the receiving device handles translation according to its own language preference and local engine.

The target flow was:

**Phone A**  
write original  
→ Firestore

**Phone B**  
receive original  
→ LanguageDetector  
→ ML Kit on-device translation  
→ display original + translation

This design is also favorable for privacy and offline fallback because the backend does not need to generate every user's translation combination.

## How far did Day 4 actually get?

On Day 4, the LocalLoopbackTransport path and receiver-side translation flow were verified in practice.

On the Firebase side, I reached basic Auth and Firestore connectivity, confirmed UID generation, and tested a Firestore write.

However, **the complete FirebaseMessageTransport and real two-instance realtime messaging remained for the next development step**.

That distinction matters.

Connecting a Firebase project is not the same as proving end-to-end user-to-user realtime messaging.

## Verification

Actually verified on Day 4:

- MessageTransport abstraction
- LocalLoopbackTransport implementation
- discovery and fix of loopback message-ID collision
- ME original → REMOTE receive → receiver-side translation
- BLE for personal peripherals / Internet for remote users
- Firebase Anonymous Auth connection
- anonymous UID issuance
- Cloud Firestore connection and write test
- canonical-message rule: Firestore carries the original

Still remaining:

- complete FirebaseMessageTransport
- bidirectional realtime messaging between two Android instances
- conversation-level message isolation
- participant authorization
- listener lifecycle verification

## What I Learned

Where boundaries are placed often matters more than implementing one more feature directly.

After introducing MessageTransport, I could reason about UI, translation, and networking independently.

Separating Bluetooth from Internet communication also simplified both the hardware and backend story.

> **The keyboard and glasses are the user's peripherals. The other user is a participant across the Internet.**

That sentence became a useful rule for the architecture that followed.

## Next

The next step is to replace LocalLoopbackTransport with a real **FirebaseMessageTransport**.

Two Android instances need to exchange original messages in both directions, while each receiver translates locally into its own preferredLanguage.

After that, the temporary room concept needs to evolve into a **participant-scoped conversation model**.
