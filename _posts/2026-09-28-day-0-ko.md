> **Day 0는 구현 결과를 기록하는 글이 아니라, 무엇을 만들 것인지 결정하고 첫 프로토타입의 방향을 잡았던 시기를 정리한 글이다. 초기 아이디어와 현재 아키텍처는 상당히 다르다.**

## 포트폴리오를 '무엇을 만들었는가'가 아니라 '왜 만들었는가'부터 시작하기

본격적인 구현에 들어가기 전, 먼저 개인 포트폴리오로 어떤 프로젝트를 만들 것인지 여러 아이디어를 검토했다.

목표는 단순히 기능이 동작하는 예제 하나를 만드는 것이 아니었다. 수업에서 다루는 **NPU, Edge AI, 모델 경량화**를 실제 사용자 문제와 연결하면서도, 모바일·임베디드·통신·AI를 함께 보여줄 수 있는 프로젝트가 필요했다.

당시에는 여러 후보를 놓고 비교했다. 대화 기록에 남아 있는 대표적인 후보 중 하나는 **피아노·오르간 독학 및 화성학 교육 시스템**이었다. 손건반과 발건반, MIDI 입력, 실시간 화성 분석과 교육 콘텐츠를 결합하는 아이디어였다. 흥미로운 프로젝트였지만, 첫 번째 프로젝트로는 다른 아이디어를 선택했다.

가장 먼저 개발하기로 한 것은 당시 **청각장애인을 위한 실시간 온디바이스 통번역 프로젝트**라고 부르던 아이디어였다.

## 왜 이 프로젝트를 1순위로 선택했는가

이 프로젝트는 한 가지 기술만 보여주는 데모가 아니라 여러 문제를 동시에 연결할 수 있었다.

- 언어 장벽을 줄이는 실시간 번역
- 청각장애 사용자를 위한 접근성
- 스마트폰 기반 모바일 애플리케이션
- BLE 기반 웨어러블 입력 장치
- 스마트글래스 기반 시각 출력
- STT와 TTS
- 오프라인 동작
- Edge AI와 모델 경량화 가능성

무엇보다 중요한 것은 기술을 전시하기 위한 프로젝트가 아니라, **실제 대화에서 시선을 잃지 않고 소통할 수 있게 한다는 명확한 사용자 문제**가 있었다는 점이다.

초기의 핵심 질문은 단순했다.

> 서로 언어가 다르거나 한쪽이 듣기 어려운 상황에서도, 두 사람이 상대의 얼굴을 보면서 자연스럽게 대화할 수 있을까?

이 질문이 이후 전체 프로젝트의 중심축이 되었다.

## 초기 프로토타입에서 정한 입출력 구조

초기 구상에서는 사용자 역할에 따라 입출력 장치를 다르게 배치했다.

### 청각장애 사용자

- **입력:** 허벅지에 착용하는 무선 키보드
- **출력:** 스마트글래스의 자막
- **보조 출력:** 스마트폰 화면

### 일반 사용자

- **입력:** 스마트폰 마이크를 통한 음성
- **출력:** 스마트폰 화면과 스피커
- **처리:** STT → 번역 → TTS

이 구조에서 가장 중요한 UX 원칙은 **Eyes-free Input / Eyes-up Output**이었다.

청각장애 사용자가 스마트폰 화면을 내려다보며 타이핑한다면 상대와 눈을 맞추기 어렵다. 그래서 손은 허벅지 키보드에 두고, 눈은 상대를 보며, 상대의 말은 스마트글래스에서 읽는 형태를 상상했다.

이 아이디어는 이후 프로젝트가 크게 확장된 뒤에도 상당 부분 살아남았다.

## 처음에는 수화 입력도 검토했다

초기 아이디어에서는 수화를 카메라로 인식해 외국어로 번역하는 방향도 검토했다.

하지만 프로토타입을 구체화하는 과정에서 이 경로는 제외했다.

수화 인식은 카메라 입력, 손·몸 자세 추적, 언어별 수화 체계, 실시간 인식 정확도 등 별도의 매우 큰 문제 영역을 만든다. 반면 허벅지 키보드는 사용자가 원하는 문장을 정확히 입력할 수 있고, BLE HID라는 성숙한 기술을 활용할 수 있다.

따라서 첫 번째 프로토타입에서는 **수화 인식을 빼고 텍스트 입력 중심으로 단순화**했다.

이 결정은 기능을 줄인 것이 아니라, 핵심 사용자 경험을 먼저 검증하기 위한 범위 조정이었다.

## 당시의 가장 큰 기술적 가정: 자체 경량 번역 모델

초기 설계에서 가장 크게 달라진 부분은 번역 엔진이다.

당시에는 오픈소스 번역 모델을 ONNX 기반으로 변환하고 INT8 양자화를 적용해 스마트폰의 NPU에서 직접 추론하는 구조를 핵심으로 생각했다. NLLB나 Gemma 계열 모델을 후보로 검토했고, 네트워크 없이 동작하는 초저지연 번역 시스템을 상상했다.

당시의 사고 흐름은 자연스러웠다.

**Edge AI 수업 → 모델 경량화 → NPU → 오프라인 번역**

하지만 이후 실제 Android 제품 구조를 검토하고 구현하면서 이 가정은 크게 바뀌었다.

범용 번역 품질과 다국어 지원을 개인 프로젝트 규모의 자체 경량 모델로 상용 엔진보다 잘 만들기는 어렵다. 제품 품질을 희생하면서까지 '직접 만든 모델'을 넣는 것은 좋은 엔지니어링 선택이 아니었다.

그래서 현재 프로젝트에서는 **Google ML Kit On-device Translation**을 기본 로컬 번역 엔진으로 사용하고, 필요할 경우 Cloud AI를 선택적으로 이용하는 구조로 진화했다.

Edge AI와 NPU는 번역 자체보다 **음성 향상, 환경음 인식처럼 오프라인·저지연 처리가 실제로 필요한 영역**에 적용하는 방향으로 이동했다.

<div class="architecture-evolution">

**Early Prototype**

Custom translation model  
→ ONNX  
→ INT8 quantization  
→ NPU inference  
→ translated output

**Current Direction**

Input  
→ Smartphone Communication Core  
→ ML Kit on-device translation / optional Cloud AI  
→ Phone / Smart Glasses / Watch output

Edge AI / NPU  
→ speech enhancement and environmental sound awareness

</div>

이 변화는 초기 설계가 실패했다는 뜻이 아니다. 오히려 프로토타입의 역할은 **가정을 드러내고, 실제 구현을 통해 더 나은 선택으로 교체하는 것**이라고 생각한다.

## 프로젝트의 범위도 달라졌다

처음에는 청각장애인을 중심으로 한 실시간 번역 시스템이었다.

그러나 입출력 구조를 계속 검토하면서 문제의 범위가 더 넓다는 것을 깨달았다.

스마트폰 키보드, 음성, 웨어러블 키보드 같은 여러 입력을 받을 수 있고, 스마트폰 UI, 스피커, 스마트글래스, 햅틱 같은 여러 출력으로 전달할 수 있다면 이 구조는 특정 장애 유형만을 위한 앱에 한정되지 않는다.

현재 프로젝트의 방향은 다음 문장으로 정리된다.

> **Any Input. Any Output. Any Language. One Conversation.**

즉 현재는 **언어와 청각의 장벽을 함께 낮추는 All-in-One Communication Solution**을 목표로 한다.

다만 Day 0에서 이 결론을 이미 알고 있었던 것처럼 쓰고 싶지는 않다. 이 방향은 초기 프로토타입에서 출발해 실제 구현과 논의를 반복하면서 만들어진 결과다.

## Day 0에서 얻은 첫 번째 교훈

이날 실제 코드는 아직 현재 제품 수준과 거리가 멀었다. 기술적 가정도 이후 상당수가 바뀌었다.

하지만 한 가지는 명확해졌다.

**좋은 포트폴리오는 기술 이름의 목록이 아니라, 해결하려는 문제와 기술 선택의 이유를 보여줘야 한다.**

NPU를 쓰기 위해 문제를 만드는 것이 아니라, 문제가 NPU를 필요로 할 때 NPU를 쓴다.  
AI를 넣기 위해 기능을 만드는 것이 아니라, AI가 사용자 경험을 실제로 개선할 때 사용한다.

이 원칙은 이후 아키텍처를 여러 번 바꾸는 기준이 되었다.

## 다음 단계
