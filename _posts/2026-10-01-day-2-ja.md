> **Day 2 では Day 1 の設計判断を実際の Android コードへ移した。言語検出から ML Kit 翻訳、モデルのダウンロードと lifecycle、Compose の会話 UI まで接続し、エミュレータ上で韓・英・日の双方向翻訳と offline 動作を確認した。**

## 目標：「できそう」を実際の Android 動作へ変える

Day 1 では、既存の Python/ONNX プロトタイプを現在の製品の基盤として使わないことを決めた。

次の問いは単純だった。

> **Google ML Kit を使い、実際の Android アプリでオンデバイス翻訳を最後までつなげられるか。**

この日は、その問いに答えるための Proof of Concept を作った。

Android/Kotlin をベースにプロジェクトを始め、Jetpack Compose UI の上へ翻訳パイプラインを段階的に追加した。

## 最初のパイプライン

初期 Android PoC の中心構成は次の通りだった。

- **LanguageDetector**：入力文字列の言語を自動検出
- **TranslationEngine**：翻訳エンジンの抽象化
- **MlKitTranslationEngine**：ML Kit の実装
- **TranslationPipeline**：検出 → 翻訳の流れを接続
- **CommunicationMessage**：会話メッセージの表現
- Compose ベースの会話画面

UI から ML Kit API を直接呼ばないようにした。

将来翻訳技術を変更しても UI と会話ロジック全体を作り直さなくて済むよう、最初から翻訳を engine boundary の内側へ置くことが目的だった。

## 最初の成功：Korean → English

最初に確認したのは、韓国語の文章を英語へ変換する単純な経路だった。

ML Kit の翻訳モデルをダウンロードした後、エミュレータ上で実際の翻訳結果が返るようになった。

重要だったのは、事前登録した単語を置き換えているのではなく、**初めて入力する一般的な文章が実際のモデルを通して翻訳されたこと**だった。

ここで、初期 Python プロトタイプと製品コードの違いが明確になった。

翻訳結果は小さな vocabulary JSON ではなく、実際のオンデバイス翻訳モデルから生成されるようになった。

## 韓・英・日 6方向テスト

一方向だけ動いても十分ではない。

初期の中心言語だった韓国語、英語、日本語について、次の六方向を確認した。

- 韓国語 → 英語
- 英語 → 韓国語
- 韓国語 → 日本語
- 日本語 → 韓国語
- 英語 → 日本語
- 日本語 → 英語

エミュレータ上でこの六方向の翻訳を確認した。

その後、サポート言語を三言語に固定しないため、ML Kit が提供する言語一覧を動的に扱う方向へ変更し、ドイツ語翻訳も追加で確認した。

この経験が、プロジェクトを「韓・英・日翻訳機」に固定しない重要なきっかけになった。

## Offline 検証

このプロジェクトにおいて on-device という言葉を単なるマーケティング表現にしたくなかった。

モデルをダウンロードした後、ネットワークに依存せず新しい文章を翻訳できるか確認した。

offline 状態でも翻訳が継続することを確認できたことで、ML Kit を現在の製品の標準ローカル翻訳エンジンとして採用する根拠ができた。

もちろん、これは「すべての言語モデルが常にインストール済み」という意味ではない。

必要なモデルは事前にダウンロードする必要があり、モデル未導入やダウンロード失敗時の UX は後で別途扱う必要がある。

## モデル lifecycle も確認する

オンデバイスモデルは、一度ダウンロードすれば終わりではない。

この日はモデル管理もテストした。

- 必要な言語モデルのダウンロード
- 特定モデルの削除
- 再ダウンロード
- 翻訳の再実行

特に日本語モデルを削除した後に再インストールし、再び翻訳できる流れを確認した。

これにより、アプリが偶然成功した一つの状態に依存するのではなく、モデル lifecycle を製品機能として扱う必要があることが分かった。

## 自動言語検出

ユーザーが毎回「今の文章は日本語」と指定する UX は、実際の会話には合わない。

そこで **LanguageDetector** をパイプラインに入れ、入力文の言語を先に検出し、その結果に応じて適切な translation pair を選ぶようにした。

これは後の受信者側翻訳アーキテクチャで非常に重要な役割を持つことになる。

相手が何語を使うかを事前固定しなくても、受け取った原文を検出してユーザーの preferred language へ翻訳できるからだ。

## 会話 UI：ME / REMOTE バブル

翻訳テストを単なる入力欄と結果表示で終わらせず、実際のコミュニケーション製品の形へ少しずつ近づけた。

会話履歴を **ME / REMOTE** のバブルとして表示し、メッセージが蓄積されるようにした。

この過程では Compose 画面の親 **Column** に付けていた vertical scroll の影響で、バブル表示が期待通りにならない問題が起きた。

原因を確認し、親側の不要なスクロール構造を取り除くことで表示を正常化した。

小さな UI 問題だが、大事な教訓だった。

翻訳エンジンが動いていても、ユーザーが結果を安定して読めなければ製品パイプラインは完成していない。

## デバイスごとの役割も整理する

この日、各デバイスの役割もより具体的にした。

### Smartphone Companion / Core

入力：
- スマートフォンキーボード
- スマートフォンマイク
- 将来の太もも BLE キーボード

出力：
- スマートフォン会話 UI
- スマートフォンのスピーカー TTS
- 将来のスマートグラス

### Smart-glasses app

スマートフォンとは別アプリとして扱い、現在の設計では **視覚出力に集中**させる方向を取った。

複雑な AI や音声処理をメガネ側へ押し込むより、スマートフォンをシステムの brain として維持する方が現実的だった。

## Verification

この日に実際に確認したこと：

- Android/Kotlin PoC の起動
- ML Kit 翻訳モデルのダウンロード
- Korean → English の実翻訳
- 韓国語・英語・日本語の 6方向翻訳
- ドイツ語まで拡張可能であることを確認
- ダウンロード済みモデルによる offline 翻訳
- モデル削除 → 再ダウンロード → 翻訳再開
- LanguageDetector の接続
- TranslationEngine / MlKitTranslationEngine 構造
- Compose の ME / REMOTE 会話 UI
- スクロール構造修正後のバブル表示正常化

当時、Galaxy 実機での検証は後続課題として残っており、この日の主要な実行検証はエミュレータ中心だった。

## What I Learned

Day 1 で「技術名ではなく実際の実行経路を確認する」と決めたなら、Day 2 ではその基準をすぐに適用した。

**On-device translation と呼ぶなら、実際にモデルをダウンロードし、ネットワークなしで新しい文章を翻訳してみなければならない。**

もう一つの大きな変化は言語スコープだった。

最初は韓国語・英語・日本語がプロジェクトの範囲のように見えていたが、実装してみるとシステムを三言語に固定する理由はなかった。

このプロジェクトは徐々に「3言語翻訳機」ではなく、**言語を拡張できる communication system**へ変わり始めた。

## Next

次の問いは、メッセージの責任をどこに置くかだった。

> **翻訳は送信者が行うべきか、それとも受信者が行うべきか。**

相手の言語を事前指定せず、各ユーザーが自分の言語だけを選べるようにするには、メッセージングと翻訳の責務をもう一度分け直す必要がある。

次の段階では、この問題を中心に **receiver-side translation architecture** を設計する。
