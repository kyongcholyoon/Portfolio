> **Day 3 の中心的な決定は、「相手の言語を事前設定しない」ことだった。メッセージは原文のまま送り、受信端末が原文の言語を検出したうえで、受信者の preferredLanguage へ翻訳する構造に変更した。**

## 問題：送信者が相手の言語を知る構造は拡張しにくい

Day 2 までに、オンデバイス翻訳そのものが Android 上で実際に動作することは確認できた。

次に問題になったのは翻訳品質ではなく、**会話の構造**だった。

例えば自分が韓国語ユーザーで、友人が日本語ユーザーなら、送信アプリが「この相手には日本語で送る」と判断して翻訳してから送信することもできる。

しかし、ユーザーと対応言語が増えるほど問題が生まれる。

- 相手が複数の言語を使う可能性がある
- 同じユーザーでも状況によって preferred language を変える
- グループ会話では同じメッセージを複数言語へ個別に変換する必要が出る
- 送信者が相手の言語設定を管理する構造は、ユーザーモデルとメッセージングを強く結合する

そこで方針を変えた。

**送信者は原文だけを責任範囲とし、翻訳は受信者側で行う。**

## UserProfile：自分が設定するのは自分の言語だけ

ユーザープロファイルに **preferredLanguage** を持たせる。

初期値は英語とし、ユーザー自身が変更できるようにする。

重要なのは、友人ごとに「この人には必ず日本語で送る」といった相手側言語設定を持たせないことだ。

送信側は原文を送る。

受信側では次の処理を行う。

1. 原文を受信する
2. 原文の言語を自動検出する
3. 自分の preferredLanguage と比較する
4. 必要ならローカルで翻訳する
5. 原文と翻訳文を一緒に表示する

この構造なら、ユーザーが preferredLanguage を変更しても、他ユーザーが保存するメッセージ形式には影響しない。

## 原文を canonical data にする

この決定は単なる UI 変更ではなく、データモデルの方向性を変えた。

メッセージの canonical data は **原文** とする。

翻訳結果は、受信者の環境や設定によって変化する derived data と考える。

この分離には複数の利点がある。

- 相手が言語設定を変えても原文はそのまま残る
- 同じメッセージを別の言語へ再翻訳できる
- 翻訳エンジンを変更しても原文を失わない
- Cloud AI を選択的に追加してもメッセージデータモデルを変える必要がない
- 将来 group conversation へ拡張しても、一つの原文を各受信者が自分の言語へ変換できる

この日の設計は、後の Firebase メッセージ構造の重要な前提になる。

## IncomingMessageProcessor で送信と受信を分離する

メッセージ処理も明確に分けた。

概念的には次のようになる。

**Sender**  
Input → Outgoing message → Transport

**Receiver**  
Incoming message → Language detection → Translation → Conversation UI

コードでも責任を分けるため、**IncomingMessage**, **IncomingMessageProcessor**, **UserProfile** といった構造を導入する方向で整理した。

UI が「相手は何語を使うか」を保持して translation pair を直接組み立てるのではなく、受信処理レイヤーが preferredLanguage を基準に翻訳を決める。

## UI 原則：原文を先に、翻訳文をその下に

翻訳アプリで原文を隠すと、ユーザーは翻訳結果を確認しにくい。

そこでバブル内の表示順序を明確にした。

1. **原文**
2. **翻訳文**
3. **言語方向**

例：

**こんにちは。今日はどうですか。**  
안녕하세요. 오늘 어떠세요?  
JA → KO

原文を primary information として保持しながら、翻訳もすぐ読めるようにするための順序だ。

この原則は、その後のメッセージ UI にも維持する。

## 自分のメッセージと相手のメッセージを分ける

自分が送信したメッセージは、自分が書いた原文そのものだ。

受信処理で自分のメッセージまで再度言語検出・翻訳すると、重複処理や UI の混乱につながる。

そこで **ME メッセージは原文中心**、**REMOTE メッセージは受信者の preferredLanguage に合わせて翻訳**する方向を取った。

この区別は、後に Firebase listener が自分のメッセージを再受信した際の重複バブル防止にもつながる。

## エミュレータ問題と実機テストへの移行

この日は Android エミュレータの不安定さにも直面した。

**System UI isn't responding** や長い startup timeout が繰り返され、すべての検証をエミュレータだけに依存するのは効率が悪いと判断した。

開発 PC の性能と emulator overhead を考慮し、その後の重要な通信・翻訳検証では実際の Android 端末も積極的に使う方向へ切り替えた。

これは機能設計とは別の話だが、開発速度に直接影響する現実的な問題だった。

## Verification

Day 3 で確定、またはコード構造に反映した主要事項：

- ユーザーに **preferredLanguage** を導入
- 友人ごとに相手の言語を事前設定しない
- 送信者は原文を送る
- 受信側で原文言語を自動検出
- 受信者の preferredLanguage へオンデバイス翻訳
- 原文を canonical message data として保持
- IncomingMessage / IncomingMessageProcessor に受信処理責任を分離
- UI は 原文 → 翻訳文 → 言語方向
- ME と REMOTE で処理責任を分離
- emulator 不安定性を受け、今後は real-device 検証を重視

この日の中心成果は大規模ネットワーク機能ではなく、その後のメッセージング全体を支える **translation ownership** を決めたことだった。

## What I Learned

最初は「どう翻訳するか」が最も難しい問題だと思っていた。

しかし実際の製品設計では、その前に

> **誰が翻訳を責任として持つべきか。**

を決める必要があった。

原文と翻訳を分離すると構造が単純になった。

メッセージはメッセージとして保存し、翻訳は受信者の現在の状況に応じて生成する。

この原則のおかげで、言語数が増えたり翻訳エンジンが変わったりしても、メッセージングの中心構造を維持できる。

## Next

次は、ローカルアプリ内でだけメッセージを作って表示する段階から抜ける。

目標は **Transport abstraction** を作り、

- local loopback で送受信パイプラインを検証し
- その後スマートフォン同士の実インターネットメッセージングへ拡張する

ことだ。

同時に、キーボードやスマートグラスといった個人周辺機器は BLE、遠隔ユーザー同士の通信はインターネット、という境界も明確にする必要がある。
