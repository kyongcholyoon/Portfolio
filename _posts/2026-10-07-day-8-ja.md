## 1. 機能より難しかった Lifecycle

リアルタイム翻訳メッセージングを作り続けると、翻訳そのものだけが難しいわけではないことがはっきりしてくる。

より難しいのは、例えば次のような状況だ。

- ログアウト後に旧アカウントの Firebase callback が遅れて届く
- target language を A → B → A と高速に変更する
- older history を取得している途中で realtime message が入る
- Friends / Profile に移動して Chat に戻る
- ViewModel が終了した後に ML Kit callback が届く
- 前の conversation の状態が別の conversation に混ざる

一つ一つは小さなバグに見える。

しかし実際の製品では、一つの race condition が、誤った翻訳、重複 listener、消えたメッセージ、別ユーザー状態の混入につながり得る。

今日はその境界を整理した。

---

## 2. Auth State を ViewModel Lifecycle の中へ

ConversationViewModel が Firebase auth-state listener を所有する形へ整理した。

アカウントが変わったときに userId だけを差し替えるのではなく、次の状態を一緒に無効化する。

- 既存 transport listener
- pending conversation operation
- profile callback
- pagination work
- translation generation
- 前アカウントの visible message
- account-owned state

基本原則は単純だ。

> **非同期処理の開始時と完了時で、同じユーザーがログインしている保証はない。**

そのため callback が戻ったときに auth generation と UID が現在の状態と一致するか再確認する。

非同期アプリでは、callback が返ってきたことよりも **その callback がまだ有効か** が重要である。

---

## 3. Receiver Language の変更は単なる設定変更ではない

preferredLanguage が変更されたとき、profile value だけが変わり、画面上の既存翻訳が前の言語のまま残る可能性があった。

特に、

1. English
2. Japanese
3. English

のように高速で切り替えた場合、古い Japanese translation が遅れて完了し、現在の English UI を上書きする可能性がある。

そこで独立した **translation generation** を導入した。

言語変更時には:

- 古い derived translation を消す
- original message は残す
- 新しい target language で再処理する
- 古い generation の結果は publish しない

Firestore の canonical message は変更しない。

server には original data を保持し、translation は receiver-side artifact として扱う。

---

## 4. Pagination State も Conversation State の一部

すでに複数ページの履歴を読み込んでいるのに、同じ conversation に戻るたび cursor が reset されると不要な refetch が発生する。

同じ conversation への reentry では:

- cursor
- initialized state
- exhaustion state
- history availability

を維持する。

別 conversation に移動した場合だけ reset する。

> **Conversation は conversationId だけではなく、現在までに取得した history window と pagination boundary を含む session state である。**

---

## 5. Failure でも既存情報を壊さない

今日改めて維持した原則は、recoverable failure がユーザーの持つ情報を破壊してはいけないということだ。

- older-history failure → loaded message を維持
- translation failure → original text を維持
- transport failure → history と draft を維持
- send rejection → draft を消さない
- explicit reentry → listener recovery
- failed translation → 後で retry 可能

失敗を state reset で解決しない。

Communication Core を demo ではなく product architecture として扱うための重要な原則である。

---

## 6. TranslationPipeline 終了後の Late Callback

ML Kit の detector、model preparation、translator は非同期で動く。

pipeline が閉じた後でも、すでに開始された callback が返る可能性がある。

そこで TranslationPipeline に明示的な closed state を追加した。

各 callback が次の段階へ進む前に:

> **この pipeline はまだ生きているか?**

を確認する。

close は単に resource を解放する操作ではない。

**今後到着する非同期 event が現在の state を変更する権利を失う境界**である。

---

## 7. 次の問題: 画面を離れると読んでいた位置を失う

24-E の後、Chat UI の continuity を改善した。

古いメッセージを読んでいる途中で Friends や Profile に移動し、Chat に戻るとリストが newest にジャンプしていた。

原因は ConversationScreen 内部だけに存在していた transient state だった。

- LazyListState
- initialScrollDone
- previousNewestId

ConversationScreen が composition から外れると、この情報も失われる。

ViewModel には message が残っているのに、**ユーザーがどこを読んでいたか** は残っていなかった。

---

## 8. List Index ではなく Message ID

現在の list index を保存するだけでは pagination に耐えられない。

older history を prepend すると、同じ message の index は変わる。

そのため viewport anchor は次の要素で保存する。

- authenticated user ID
- conversation ID
- first visible stable message ID
- first-visible pixel offset
- near-newest state

復元時には保存した message ID を現在の list で再検索する。

index が変わっても message identity は変わらない。

---

## 9. User Intent を維持する

復元には二つのモードがある。

### 古い履歴を読んでいた場合

画面外で new realtime message が届いても元の reading position を維持する。

### newest 付近にいた場合

戻った時点の newest area に移動する。

単純な scroll persistence ではなく:

> **過去を読んでいたなら過去を維持し、最新を見ていたなら最新を追う。**

という user intent を維持する。

---

## 10. Viewport の User / Conversation Isolation

viewport key は conversation ID だけではない。

**userId + conversationId**

で分離した。

これにより:

- User A / Conversation X
- User B / Conversation X
- Conversation X / Conversation Y

の reading state が混ざらない。

UI state も multi-user application では ownership を持つ。

## 11. Debugging: Build Failure も開発の一部

今日の build は最初からすべて成功したわけではない。

- sandbox から Gradle cache lock へアクセスできない問題
- incremental Kotlin compiler の一時的な symbol resolution failure
- PowerShell で Gradle property を渡す際の quoting mistake
- JVM test fixture の CommunicationMessage 必須引数不足

それぞれを production code、build environment、compiler state、test fixture に分離して原因を確認した。

最終的には normal Kotlin settings でも再 build し、temporary workaround に依存した成功ではないことを確認した。

> **Build failure は診断そのものではない。まず、どの layer が失敗しているかを特定する必要がある。**

## 14. Learning

今日の作業は一つの原則に集約できる。

> **Every asynchronous result must prove that it still belongs to the current session.**

message には owner がある。

translation work にも owner がある。

callback には generation がある。

viewport には user と conversation がある。

lifecycle が終了したなら、その後届いた event に現在の state を変更する権利を与えてはいけない。
